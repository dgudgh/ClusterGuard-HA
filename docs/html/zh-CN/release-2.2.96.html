ClusterGuard HA 2.2-96#

日期：2026-09-09。范围：修复灾难恢复未接入操作锁的问题，供用户手动升级。

根因与修复#

旧版 dc1a57a 的主库切换、旧主恢复在按钮和执行函数两处检查 switchUnlocked。后续新增的灾难恢复入口、预检和提交遗漏了该条件，而且将锁按钮设置为 hidden，却又被按钮 CSS 显示出来。2.2-95 中已用 MySQL/PG 隔离浏览器复现，详细修改前证据见 操作锁回归记录。

  • 三个操作标签共用可见操作锁。未解锁时不能进入灾难恢复、重新预检或提交；即使直接触发事件，处理函数仍检查锁定状态。
  • 重新锁定、刷新、换集群、关闭窗口或会话失效后，旧确认不再有效；迟到预检不会重新点亮执行。
  • 保留集群名称和隔离风险二次确认、重复提交保护；关闭弹窗不会取消后台恢复任务。
  • 无拓扑时，管理员仍可针对已确认的集群元数据显式解锁，再接受后端恢复预检。普通主库切换不放宽原有观测门禁。
  • 与 2.2-95 的静态 HTML 和 CSS 完全一致。保留已经确认的日志工具栏、集群联动、20 条分页和完整历史。

没有修改数据库恢复算法、签名协议、后台授权、fencing、writer lease、维护门禁或多数派规则。

测试边界#

全量 Go 测试、vet、API 全量竞态测试通过。操作锁 8 组、既有恢复弹窗 7 类、日志联动 9 项、分页 7 项及 1,000 条日志上下文隔离浏览器回归通过。浏览器使用实际控制台 HTML 和隔离 API，恢复提交只命中模拟服务，不是现场灾难恢复测试。

用户在“设置 → 版本更新 → 升级”上传对应 .cgupgrade，不要直接安装 RPM 绕过门禁。升级完成后，锁定状态的一键恢复应为禁用；管理员解锁后才能进入预检，最终仍须确认集群名称及隔离风险。

没有 SSH、没有现场上传、没有执行真实滚动升级或数据库恢复，也没有删除现场日志。此前 P0 的完整真实数据库恢复验收不能由本次前端回归代替。
