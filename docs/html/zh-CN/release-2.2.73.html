ClusterGuard HA 2.2-73：滚动升级执行与最终状态闭环#

日期：2026-09-07。架构：Linux x86_64。现场最终验收来源：2.2-72。

已定位的根因#

  1. 三台源节点的 clusterguard-agent-reconcile.timer 都未运行。旧升级器安装 RPM 后没有恢复该单元，却把它作为节点就绪条件，导致目标版本和自动回退均等待超时。
  2. 旧执行器异常退出后，原执行节点已有失败终态，跟随节点仍保存运行状态；换 Leader 后旧状态重新阻塞升级入口。
  3. 页面从所有历史升级中寻找任何 maintenance_active=true 的记录。新升级成功后，它重新选中旧失败记录，误报当前仍在回退。

修复范围#

  • 包含 2.2-72 的节点服务恢复、真实墙钟超时、执行所有权、异常终态记录和 Raft 升级维护门禁修复，详见 release-2.2.72.md。
  • 页面按实际执行时间选取最新升级任务；新成功终态不再被旧失败或旧运行记录覆盖。
  • 升级轮询同时读取控制面实际维护状态。历史维护标记不能推翻当前已释放的门禁；确有无主维护门禁时仍显示待核验，不静默解除保护。
  • 新上传和只读计划不掩盖上一轮尚未收口的执行；排队执行仍保留保护；原始失败日志继续可查。
  • 增加执行真实页面 JavaScript 的回归测试，覆盖成功后旧失败、旧运行、上传未执行、计划运行、排队、不可读任务和维护状态未知。

验收边界#

2.2-68 到 2.2-72 已经通过真实 Chrome 上传、签名校验、计划、补丁 ID 确认和三节点 RPM 滚动安装。该轮发现页面旧状态回退问题，因此不作为最终交付验收结论。

源版本的失败维护锁曾阻断上传入口，恢复时使用已验签 RPM 内的控制面程序作临时入口，未修改数据库、未删除维护标记；随后完成正式浏览器升级。三台临时 systemd 覆盖项均已撤销，正式运行程序恢复为 /usr/local/bin/clusterguard。历史状态恢复仅复制原执行节点已经存在的失败终态，保留旧状态备份及全部事件和日志。

最终交付以发布目录中的 ACCEPTANCE.md 为准。PostgreSQL 灾难恢复、主库启动与 50 个健康 discovery 周期不能用平台升级成功代替；若数据库服务仍处于停止状态，必须明确记录未通过，不能放宽健康评估或 fencing。
