已验证的 MySQL 高可用方法#

目的#

本文档记录了在之前的原型中验证过的生产行为和实验室场景，并有意在独立的 ClusterGuard HA 控制平面中重新实现。它仅作为行为参考。不继承任何源代码包、API、表、配置键、可执行文件或产品名称。

稳定资源标识#

在物理主机能够被管理之前，它会获得两个稳定的标识：

  • 不可变的平台 resource_id UUID；
  • 全局唯一且不可变的操作员面向的 node_name，例如 cg-data-0001。

MySQL 实例另外绑定到原生的 server_uuid。主机名、IP、端口、显示名称和端点别名是可变的坐标。坐标更改会更新现有资源并保留旧地址作为别名；它不能创建另一个节点或实例。

当前实现：

  • internal/store/nodes.go 强制全局节点名称唯一性和不可变性；
  • 发现过程通过 MySQL server_uuid 绑定观察结果，然后关联注册的节点 UUID；
  • 元数据同步在更新数据库端点时保留平台和原生标识；
  • 控制台分别显示 node_name、资源 UUID、server_uuid 和可变坐标。

集群清单边界#

ClusterGuard 仅控制所选集群清单中的资源。请求不能在发现或执行期间引入任意端点。操作计划携带集群、源、目标、拓扑观察和资源修订。坐标或清单更改会使旧计划失效。

集群显示名称是稳定的操作员标签。选择集群从不依赖于当前主主机名，因此切换主节点不会重命名或复制集群。

故障观察窗口#

自动恢复使用稳定事件而不是单个失败探测。默认需要连续 4 次当前失败观测，且时间跨度不少于 3 秒。对于相同源主节点和事件，成功或不确定的恢复不能再次提交。失败的预提交尝试只能在配置的退避后重试。

自动恢复还需要以下内容：

  • 当前的 Raft 主节点；
  • 控制器多数；
  • 新鲜完整的拓扑证据；
  • 恰好一个失败或未知的记录主节点；
  • 合格的一级候选者；
  • 隔离和端点租约证据；
  • 正常的持久操作工作流程。

写主与 VIP 绑定#

写主角色更改和 VIP 转移是一次操作。执行后，成功需要以下所有条件：

  • 恰好一个可写的 MySQL 实例；
  • 恰好一个 VIP 拥有者；
  • VIP 拥有者是已验证的主节点；
  • 每个可到达的从节点都连接到该主节点；
  • 不完整的主机探测不被视为成功。

端点租约由多数支持并由主节点签发。无法续订有效多数租约的节点会移除本地 VIP 并强制只读。因此，恢复的旧主节点不能作为第二个写主返回或保留写主端点。

受控切换与旧主节点恢复#

计划切换遵循共享工作流程：

DISCOVER -> PRECHECK -> PLAN -> SAFETY_GUARD -> LOCK -> APPROVE -> EXECUTE -> VERIFY -> AUDIT -> REPORT

MySQL 适配器对源进行隔离，追赶选定的候选者，提升它，重新父化从节点，转移 VIP，并验证最终不变量。提交后验证间隙是 indeterminate，从不成功。

旧主节点恢复始终将节点作为当前主节点的只读副本返回。安全的 GTID 子集可能使用快速重新连接。数据不一致、缺失或物理替换使用与添加节点相同的重建管道。

节点添加与重建管道#

添加节点和修复物理损坏的节点使用一个持久生命周期工作流程：

  1. 验证注册的集群、固定的节点标识、端点唯一性、包可用性、供体健康状况和操作并发性；
  2. 安装选定的 MySQL 版本，但不创建独立的写主；
  3. 保持目标只读；
  4. 从显式能力中选择 Clone、XtraBackup 或逻辑转储；
  5. 配置与当前主节点版本兼容的复制；
  6. 验证原生标识、源、线程、延迟、只读状态和本地 VIP 的缺失；
  7. 仅在验证后提交节点和实例元数据。

重建会重用原始资源 UUID 和固定节点名称。数据节点数量不受限制。控制器或混合节点更改必须以至少三个的奇数成员结束，并作为一次验证的成员更改提交。

逻辑转储回退故意在供体导入前清除目标上的每个非系统模式。这防止物理替换或数据不一致的目标在 GTID 状态重置后保留仅目标数据。它仅在受保护的重建工作流程中允许，且从不作为隐式修复运行。

计划重启#

受管理的 MySQL 重启是一个操作，而不是原始服务重启。它将实例置于维护状态，抑制审批窗口内的自动恢复，重启 MySQL，验证就绪状态和发现，验证 VIP 唯一性，然后才移除维护状态。失败会使恢复抑制可见，并需要操作员审查，而不是静默重新开启自动操作。

安装与配置#

最终安装程序必须接受准备好的 ClusterGuard 包和目标主机清单，在变更操作前执行所有预检，并为服务器、代理、端点同步和 systemd 单元生成一个共享配置源。秘密通过受保护的服务器端环境引用提供，从不写入任务历史或 API 响应。

安装流程是分阶段且幂等的：预检、复制、安装、配置、启动、注册、同步、验证和报告。重新运行已完成的阶段会检查其后置条件，而不是盲目重放它。

操作员可见性#

控制台为全局概览、选定集群拓扑、受保护操作、节点生命周期、指标、操作日志、产品信息和设置提供独立视图。每个可见的执行操作要么调用真实的 ClusterGuard API，要么由于后端能力原因被禁用。原始操作证据默认折叠，但可用于审计。

验证交付#

rc61 包（clusterguard-ha-mysql-parity-rc61-linux-amd64.tar.gz，即验收矩阵中记录的构建产物）包含控制器、CLI、受限代理、生命周期执行器、systemd 单元、定时器、日志轮转、配置模板和安装程序。它被部署到三个控制器和三个共置的数据节点上。接受矩阵验证了六个集群、50 次重复的真实切换、多数丢失的自我隔离、主网络故障、旧主节点返回、重复重启、完整主机重启、数据不一致重建和端点元数据同步。详细证据记录在 docs/mysql-feature-parity-acceptance.md 中。

仍需环境特定的生产强化：

  • 配置并测试外部隔离提供者，以部署平台的虚拟化器、云、PDU 或 BMC API；
  • 为每个支持的 MySQL 家族验证 Clone 或确切的 XtraBackup 构建；
  • 建立备份/恢复、保留和恢复时间目标；
  • 集成外部警报传递和长期指标保留；
  • 在生产启用前，在目标内核、网络、存储和 MySQL 包上重复破坏性矩阵。
