ClusterGuard HA MySQL 8.0 / 8.4 生产资格验证#

日期：2026-07-28 环境：192.168.102.152-154，三控制节点、三数据节点 版本：MySQL 8.0.44（3306）、MySQL 8.4.10（3384）

结论#

当前版本通过功能、故障、安全和数据完整性验证，可进入受控生产试运行。 在以下上线条件全部落实前，不定义为“无条件生产就绪”：

  1. 网络隔离场景没有外部 STONITH/fencing 时，系统选择阻断接管以避免双主；若业务要求该场景仍可用，必须接入独立电源、虚拟化或交换机 fencing。
  2. 六个实例已启用半同步复制，切换和故障接管会在 VIP 漂移前验证新主半同步状态和 ACK 客户端；本次测试未发现已确认事务丢失，但半同步仍不等于跨所有故障类型的绝对 RPO=0。
  3. 自动故障恢复的客户端最大中断实测为 51.729-60.108 秒。若生产 SLA 要求自动恢复 RTO 不超过 30 秒，当前版本不满足，不能直接上线。
  4. 业务连接池必须设置连接、读写超时并支持断线重连和幂等重试；VIP 漂移不会自动修复已建立且卡住的 TCP 会话。
  5. 测试控制台使用未受信任的自签名证书，浏览器自动化拒绝绕过证书校验。生产部署必须使用受客户端信任、SAN 正确的 TLS 证书后，再完成一次真实页面切换验收。

最终并发故障验证#

同时对两套主库执行硬故障，持续运行 16 路写入（每个版本 8 路），随后启动旧主并通过正式回挂工作流恢复。

版本 写入流 尝试 已确认 失败重试 最大中断 完整性
MySQL 8.0.44 8 14,378 13,948 430 60.236s 通过
MySQL 8.4.10 8 14,058 13,850 208 60.057s 通过

完整性判定：

  • 16/16 报告生成成功。
  • 所有流 observed.count == acknowledged。
  • 所有流序号从 1 连续到 acknowledged。
  • 0 个校验失败，0 个计数不一致，0 个序号缺口。
  • 故障期间未观察到“VIP 已离开但旧主仍可写”。

最终状态：

  • MySQL 8.0：192.168.102.154 为主库，VIP 192.168.102.155 唯一绑定；其余两节点为健康从库，延迟 0。
  • MySQL 8.4：192.168.102.153 为主库，VIP 192.168.102.160 唯一绑定；其余两节点为健康从库，延迟 0。
  • 两个旧主均通过正式回挂工作流恢复，复制 IO/SQL 线程运行。
  • 三个 ClusterGuard 控制节点均为 active、live、ready。

本轮缺陷修复与回归#

双集群自动恢复队头阻塞#

恢复调度器原先会同步等待一个集群的完整 RunOnce，导致另一集群的故障恢复被前一个集群阻塞。本轮改为：

  • 每个集群独立异步执行恢复周期。
  • 同一集群以 inFlight 状态避免重复恢复。
  • 全局恢复并发使用容量为 4 的有界门控。
  • 新增错峰双集群故障测试，证明第二个集群可在第一个集群完成前进入工作流。

修复后同时停止两套主库的回归结果：

版本 尝试 已确认 失败重试 最大中断 完整性
MySQL 8.0.44 1,396 1,331 65 58.126s 通过
MySQL 8.4.10 1,350 1,319 31 60.108s 通过

两个写入流均满足 observed.count == acknowledged，序号从 1 连续到最后一个已确认事务。旧主启动后保持 read_only=1、super_read_only=1 且不持有 VIP，随后通过正式回挂工作流恢复。

半同步切换门禁#

  • 计划切换和故障接管在 VIP 转移前激活并确认新主半同步状态。
  • 半同步激活失败时，新主重新进入只读并阻断 VIP 转移。
  • smoke 检查主库半同步 source、ACK 客户端数量和从库半同步 replica 状态。

候选和审批时序#

  • 人工停止候选节点 SQL 线程后，预检查在授权和执行前阻断，主库与 VIP 均未变化。
  • 对健康候选生成一次性审批后，再停止其 SQL 线程；使用旧审批执行时被判定为 stale_plan，未发生角色或 VIP 变更。
  • 自动恢复调度、候选阻断和旧审批失效均增加了回归测试。

已覆盖故障矩阵#

  • 计划切换、双集群同时切换、同集群并发切换互斥。
  • 主库进程硬停止、两套主库同时硬停止、旧主恢复与正式回挂。
  • 主库计划重启、从库重启、全站 MySQL 冷停冷启。
  • ClusterGuard 进程 SIGKILL、Raft Leader 停止和重新选举。
  • 控制节点多数丢失、单节点真实网络隔离、恢复后收敛。
  • VIP 唯一性、主库与 VIP 强绑定、重启防写、无多数派自隔离。
  • 复制 IO/SQL 线程停止、候选节点阻断、恢复后重新评估。
  • GTID、复制位点、候选资格、旧主回挂和复制链路验证。
  • 273/300 连接压力下切换。
  • 每版本 8 路持续并发写入下的同时故障切换。
  • MySQL 持久化参数、内存配置、systemd 停止语义和冷启动角色。
  • 半同步 source/replica、ACK 客户端和切换前激活失败回滚。
  • 候选 SQL 线程停止、拓扑变化后的旧审批失效。
  • 双集群错峰故障的恢复调度并发，避免跨集群队头阻塞。
  • 三节点日志、failed unit、panic/fatal、InnoDB 损坏关键字巡检。

关键实测#

  • 15 分钟双版本故障穿越：
    • 8.0：9,602 次已确认写入，最大中断 64.625s，完整性通过。
    • 8.4：9,721 次已确认写入，最大中断 58.061s，完整性通过。
  • 计划主库重启：
    • 8.0：最大中断 22.601s，完整性通过。
    • 8.4：最大中断 18.924s，完整性通过。
  • 连接压力切换：
    • 8.0：最大中断 6.503s。
    • 8.4：最大中断 7.130s。
  • 控制多数派丢失：
    • 两个 VIP 均移除，原主均进入只读；恢复后完整性通过。
  • 三台 MySQL 同时冷停冷启：
    • 8.0 最大中断 92.047s，8.4 最大中断 75.364s，完整性通过。

数据持久性与配置#

六个实例均确认：

  • sync_binlog=1
  • innodb_flush_log_at_trx_commit=1
  • relay_log_recovery=1
  • log_replica_updates=1
  • GTID 开启
  • binlog format 为 ROW
  • 半同步复制插件已启用
  • 当前主库半同步 source 为 ON，且有 2 个 ACK 客户端
  • 两个从库半同步 replica 状态为 ON

旧主或节点重启时，磁盘持久化只读配置先于服务恢复生效；拓扑收敛前不会自动恢复写权限。

上线前动作#

  1. 明确网络分区可用性策略：接受 fail-closed，或接入并演练外部 fencing。
  2. 明确 RTO：当前自动故障恢复最大中断约 60 秒；硬性要求 30 秒时必须继续优化并重新跑完整矩阵。
  3. 明确 RPO：接受半同步复制的边界，并为存储、网络和双节点故障制定恢复策略。
  4. 在应用侧验证连接/读/写超时、断线重连和幂等重试。
  5. 部署受信任 TLS 证书，并用正式浏览器控制台完成切换、回切和审计查看。
  6. 复核历史审计中的 15 条 indeterminate 记录；它们不是当前活动操作，但上线前应完成归档说明。
  7. 监控 Raft 数据文件、磁盘余量、VIP 唯一性、半同步状态、复制线程和复制延迟。
  8. 先灰度一套非核心业务，保留回退窗口，再逐步扩大生产范围。
