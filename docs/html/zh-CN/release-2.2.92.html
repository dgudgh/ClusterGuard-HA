ClusterGuard HA 2.2-92：保持原页面，分离历史日志与刷新#

日期：2026-09-08。适用源版本 2.2-91，目标版本 2.2-92，架构 x86_64。用户手动上传更新，本轮没有部署现场。

页面保持不变#

从已发布 91 RPM 的控制程序中提取实际内嵌 HTML，核对 SHA-256：

593925c4ff99317310650366969b783eb0af4f880df19e7a4cc0b03442e97b00

以该文件为基线，只迁移功能性 JavaScript 修改。92 的静态 HTML、CSS、布局、图标、页签与工具栏和 91 逐字节一致。不包含本地设计预览里的新导航、资源区、最近操作区或指标图形。不改变既有红框搜索筛选优化。

功能修复#

  • 集群刷新不再读取全部操作摘要。新增轻量 operations?view=context，按集群提供完整运行中/待复核计数以及所有历史主库身份，避免历史记录越多刷新越慢。
  • 完整操作日志进入日志页后加载，保留全量筛选、分页展示、原始证据展开和失败重试；切换集群不重建隐藏日志列表，也不重置已展开记录和分页位置。
  • 上下文不可用、返回格式不符或集群身份不匹配时，操作继续锁定。保留 observation 一致性校验、旧请求取消、迟到响应防覆盖和后端全部授权。
  • 总览待复核数量由完整记录计数生成，不能只计算最近几条；引擎数量使用实际注册集群，修正误计为适配器支持数量的问题。
  • 不删除日志，不修改安装材料默认保留 3 个版本的策略，不修改数据库恢复、fencing、VIP、writer lease、Raft 仲裁或升级器。

验证结果#

  • go test ./...、go vet ./... 通过；相关 API/Store/Console 的 -race 测试通过。需要外部数据库的条件测试不等于本轮现场验收。
  • 实际已发布 91 HTML 对比 92 HTML，在相同隔离 API、1,000 条记录、历史请求人为延迟 2,400 ms 下：
条件 91 92
首次刷新完成 4,981 ms 76 ms
三次切换完成（PG / MySQL / PG） 2,497 / 2,427 / 2,417 ms 34 / 15 / 17 ms
日志请求未返回时切换 MySQL / PG 受历史等待影响 11 / 15 ms

这些是模拟延迟的本地真实页面测试，不是现场性能保证。另验证 1,000 条日志完整可读、最旧运行中/待复核记录计数、旧主身份、日志错误隔离、原始证据和分页保留、上下文缺失锁定、旧响应防覆盖。

  • 页面回归：12 次集群切换、24 组不同尺寸页面、超时/503/409/乱序、三组可切换标签、升级初始空态、默认折叠日志和固定摘要独立滚动。
  • 与上一版升级包使用同一实验室公钥验签，使用真实引导器 --inspect 通过；篡改清单被拒绝，清单和全部载荷摘要一致。
  • 新包内原版 91 回退 RPM 与已发布文件逐字节一致，92 控制程序内嵌 HTML 与验收源文件一致。
  • RPM 文件清单相同，66 个非二进制/构建信息文件未改变，升级脚本、服务配置与运行时配置样例均与 91 相同。五个程序重新构建并标记 92 版。

手动更新#

确认当前节点版本为 2.2-91，然后在“设置 → 版本更新 → 升级”选择 .cgupgrade，上传并等待校验完成，确认源版本 91 和目标版本 92，再执行滚动升级。不是直接安装 RPM，也不需要更换公钥。

升级后核对三节点版本、维护门禁释放、MySQL/PG 的刷新完成耗时、完整日志计数和原始详情；页面应继续是原来的经典风格。若来源版本或签名校验不符，应停止，不跳过校验。
