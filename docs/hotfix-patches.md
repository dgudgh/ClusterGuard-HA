> exist on disk. Do not edit by hand — rebuild the patch and re-render instead.
> `tools/verify-hotfix-patch-catalog.cjs` fails when a fix commit has no patch or
> when this file disagrees with the artifacts.

A `.cgupgrade` carries whole RPMs and can only be applied by the rolling upgrade
executor. A hotfix patch carries exactly what one bug fix changed: the rebuilt
binaries, the systemd units it touched, the source diff as evidence, and an
apply/rollback pair. Every bug fix against a released version must leave one behind,
otherwise a running site can only pick the fix up by waiting for the next release.

## Applying a patch

```bash
tar -xzf release/2.2-103-hotfixes/<artifact>.cgpatch
cd clusterguard-hotfix
bash apply.sh            # backs up, verifies SHA-256, installs, daemon-reload
systemctl restart <unit> # apply.sh prints the units it needs; it never restarts by itself
bash rollback.sh         # restores from the newest backup manifest
```

## HF-2026-0928-04 — The console froze on a dead dialog after a host power-off was submitted

- Severity: P1
- Fix commit: `5ae2039` (baseline `467e533`)
- Applies to: 2.2-103 → 2.2-103+hf-2026-0928-04 (x86_64)
- Artifact: `release/2.2-103-hotfixes/clusterguard-ha-hotfix-HF-2026-0928-04-2.2-103.x86_64.cgpatch`
- SHA-256: `ae4ab5f0538d8c78a9aea20e399c1b7fee8c7d8fb1b316e81f8c081bbfc247cb`
- Source diff: `src/HF-2026-0928-04-5ae2039.patch`
- Payload:
  - `payload/bin/clusterguard` → `/usr/local/bin/clusterguard` (0755)
- Restart required: `clusterguard-ha.service`

### Symptom

After a host power-off was submitted the control plane went away with the host, leaving the page parked on the confirmation dialog forever, and a lost response after submission was reported as an error.

### Root cause

The poweroff branch only updated the result banner after a successful submission; it never closed the dialog or settled the page, and a lost response after submission is an expected outcome rather than an error.

### Fix

settlePoweroffConsole() waits 2.5s then probes /power/status with a 3s timeout: unreachable shows the offline screen and closes the tab, reachable only closes the dialog and starts a 5s watchdog. Service mode never closes the page.

### When to apply

- 提交整机关机后控制台卡死、需要手动关闭标签页
- 关机提交后偶发“无法连接控制 API”被当作失败

### Verification

- `/usr/local/bin/clusterguard --version`
- `systemctl is-active clusterguard-ha`
- `curl -sk --max-time 5 https://127.0.0.1:3000/api/v1/clusters | head -c 200`

### Rollback

执行 rollback.sh 恢复旧控制面二进制后 systemctl restart clusterguard-ha；页面将恢复为提交后停留在对话框的旧行为。

## HF-2026-0928-03 — MySQL writer reconcile flap: the authorized primary fenced itself every five seconds

- Severity: P0
- Fix commit: `dd82ca5` (baseline `467e533`)
- Applies to: 2.2-103 → 2.2-103+hf-2026-0928-03 (x86_64)
- Artifact: `release/2.2-103-hotfixes/clusterguard-ha-hotfix-HF-2026-0928-03-2.2-103.x86_64.cgpatch`
- SHA-256: `c4ebf0ad6f384cd71c28c460ffb47dd8931e6dc6dc021ee3a0f49e76fba4ce8e`
- Source diff: `src/HF-2026-0928-03-dd82ca5.patch`
- Payload:
  - `payload/bin/clusterguard-agent` → `/usr/local/bin/clusterguard-agent` (0755)
  - `payload/systemd/clusterguard-agent-reconcile.service` → `/usr/lib/systemd/system/clusterguard-agent-reconcile.service` (0644)
- Restart required: `clusterguard-agent-reconcile.service`

### Symptom

The cluster never left degraded, both replication links never left unhealthy, candidate evaluation answered 409 and every planned shutdown was blocked. Measurement showed 9,492 self-isolations since install, with read_only and the VIP flipping together roughly every ten seconds.

### Root cause

The reconcile unit bounded capabilities without CAP_DAC_OVERRIDE/CAP_DAC_READ_SEARCH, so root could not read <datadir>/mysqld-auto.cnf (mysql:mysql 0640) and the fail-closed loop self-isolated; and convergeWritableRestartState demanded RestartReadOnly to clear even though restarting read-only is a permanent site invariant the role controller re-asserts on every mutation.

### Fix

Convergence now requires only that the recorded isolation intent is clear and the runtime is writable; the restart fence is left alone. The unit keeps CAP_DAC_OVERRIDE and CAP_DAC_READ_SEARCH in both the bounding and ambient sets.

### When to apply

- 集群长期 degraded 且复制链路 unhealthy，但复制本身正常
- journalctl -u clusterguard-agent-reconcile.service 反复出现 self-isolated 或 permission denied

### Verification

- `/usr/local/bin/clusterguard-agent --version`
- `systemctl show clusterguard-agent-reconcile.service -p CapabilityBoundingSet`
- `journalctl -u clusterguard-agent-reconcile.service --since '-10min' | grep -c self-isolated`
- `jq -c '.topology_snapshots[] | {observed_at, health: .health.state}' /var/lib/clusterguard/metadata.json`

### Rollback

执行 rollback.sh 恢复旧二进制与旧单元后 systemctl daemon-reload；注意回滚会重新引入抖动，仅在确认新二进制有回归时使用。

## HF-2026-0928-02 — Two update prerequisites: SSH key ownership and a shared runtime directory the helper owned

- Severity: P0
- Fix commit: `d5f9491` (baseline `467e533`)
- Applies to: 2.2-103 → 2.2-103+hf-2026-0928-02 (x86_64)
- Artifact: `release/2.2-103-hotfixes/clusterguard-ha-hotfix-HF-2026-0928-02-2.2-103.x86_64.cgpatch`
- SHA-256: `b775702291798ffa18f7911bae70c34394d1c9dae2228cbf07a6fecee4e56132`
- Source diff: `src/HF-2026-0928-02-d5f9491.patch`
- Payload:
  - `payload/systemd/clusterguard-update-helper.service` → `/usr/lib/systemd/system/clusterguard-update-helper.service` (0644)
  - `payload/installer/install_clusterguard.sh` → `installer-only, no site path` (0755)
- Restart required: `clusterguard-update-helper.service`

### Symptom

Software updates stayed available=false and the three upload controls stayed disabled; even with a hand-written update.json the executor rejected the SSH key as too permissive, and the helper failed its first start with status=233 while deleting the shared /run/clusterguard on stop.

### Root cause

The generated update.json pointed ssh_key at a clusterguard-owned private key while the workspace file check requires root ownership with no group or other write bit; and the helper unit declared RuntimeDirectory=clusterguard, which races with start-up chown/chmod and is deleted by systemd on stop.

### Fix

The installer now also installs a root:root 0600 key copy at /etc/clusterguard/updates/controller_ed25519 and points update.json at it; the helper unit drops RuntimeDirectory for an idempotent ExecStartPre that creates /run/clusterguard without owning it.

### When to apply

- 控制台版本更新长期 available=false
- clusterguard-update-helper 首启失败或停机后 /run/clusterguard 丢失

### Verification

- `systemctl cat clusterguard-update-helper.service | grep -c RuntimeDirectory`
- `systemctl is-active clusterguard-update-helper`
- `stat -c '%U:%G %a' /etc/clusterguard/updates/controller_ed25519`
- `curl -sk https://127.0.0.1:3000/api/v1/platform/updates | head -c 400`

### Rollback

执行 rollback.sh 恢复旧单元后 systemctl daemon-reload；注意旧单元重新拥有 /run/clusterguard，停机时会再次删除该目录。

## HF-2026-0928-01 — The console stopped explaining why a capability is unavailable

- Severity: P1
- Fix commit: `ed9faca` (baseline `467e533`)
- Applies to: 2.2-103 → 2.2-103+hf-2026-0928-01 (x86_64)
- Artifact: `release/2.2-103-hotfixes/clusterguard-ha-hotfix-HF-2026-0928-01-2.2-103.x86_64.cgpatch`
- SHA-256: `b860c87db4d9d0bac129b2bf41d3dad3ed6f966cdac99c0e3ede5cf4105647af`
- Source diff: `src/HF-2026-0928-01-ed9faca.patch`
- Payload:
  - `payload/bin/clusterguard` → `/usr/local/bin/clusterguard` (0755)
- Restart required: `clusterguard-ha.service`

### Symptom

The software update panel showed only a red "unavailable" badge with no reason, and the cluster load banner named the failing section without saying why, so operators could not tell what to do next.

### Root cause

The front end discarded the reason the API already returned: the evidence result kept only a boolean state and never fed the 409 body back into the panel or the banner, so only a status label survived.

### Fix

The panel now renders an inline reason and puts it on the badge tooltip; the evidence result carries `reason`, `evidenceReasonText()` maps the 409 message to readable text, and `evidenceUnavailableText()` reports it per section.

### When to apply

- 控制台版本更新面板显示“不可用”但无原因
- 集群加载横幅只报栏目名、不报原因

### Verification

- `/usr/local/bin/clusterguard --version`
- `systemctl is-active clusterguard-ha`
- `curl -sk https://127.0.0.1:3000/api/v1/platform/updates | head -c 400`

### Rollback

执行 rollback.sh 后 systemctl daemon-reload 并 systemctl restart clusterguard-ha；控制台将恢复为只显示状态标签的旧行为。
