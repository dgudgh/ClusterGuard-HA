# 修改与证据规则

适用：修改任何业务代码前；文档整理时仅核对对应文档基线。

任何修改前先读[门禁执行与更新流程](../../zh-CN/validation-gate-workflow.md)，记录适用阶段和验证计划；涉及契约 §20 范围时，修改/执行前完整读[强制契约 v2](../../zh-CN/upgrade-validation-chain.md)。完成门禁必读后再执行下列对照与当前功能阅读。

**没有完成旧版对比，不得修改业务代码；没有完成行为回归，不得宣称修复或交付升级包。**

1. 先确认实际源码目录、分支、HEAD、未提交改动和目标运行版本。不得把预览页面、RPM、其他工作树当作当前源码；不得覆盖他人未提交改动。
2. 在第一次业务代码编辑之前，读取本规则和当前功能文档；涉及构建、发布或现场交付时再读取相关发布验收文档。用 `git log`、`git show`、`git diff` 找到用户认可的旧行为、相关变更及其父版本。只看当前 HEAD 或当前实现不算对比旧版。
3. 区分“旧版正确行为”“引入回归的提交”“当前工作树”“当前发布包”。用户说旧版正常时，必须追溯实际旧实现，不能先解释成用户误用、网络慢或数据库本身慢。
4. 对照完整调用链：入口事件、默认状态、查询参数、作用范围、加载与错误状态、异步更新、缓存/游标、持久化和最终展示。不能只对比样式或函数名。
5. 修改前将对比证据写入本次任务 Markdown：基线提交/版本、文件及函数、旧行为、新行为、回归位置、复现方法、必须保持的不变量和拟改范围。口头说“看过旧代码”不算完成。
6. 优先用同一组用户路径在修改前复现失败，再修改，再验证通过。无法运行旧版时，明确记录限制和可取得的源码/包证据，禁止编造测试通过。
7. 缺少旧源码、可信基线或关键行为证据时，先继续只读调查或向用户索取；不得用猜测替代前置检查并继续改动。

## 必须保持与回归

- 旧版本的正确交互应恢复，旧版本的已知性能和安全缺陷不得一并恢复。局部修复，不做无关重构。
- 区分本地源码测试、隔离浏览器测试、真实现场验收。未做现场上传、验签和滚动升级，不得写成现场已验收。
- 性能修复不能恢复全量日志阻塞页面刷新，也不能靠取消健康核验、观测一致性、签名、权限、fencing、writer lease、维护门禁或多数派检查变快。

## 文档变更必须登记

- 任何 Markdown 的新增、删除、修改都要在[Markdown 变更记录](../markdown-change-record.md)登记：文件路径、变更类型（`A` 新增 / `M` 修改 / `D` 删除）、改了什么。重命名按「删旧 + 增新」两条记。
- 登记后执行 `node tools/verify-markdown-change-record.cjs`，必须 passed。它按台账基线计算「基线 → 当前工作树」的每个 md 变更，逐个比对：**变了没登记**、**登记了但类型不符**、**登记了但根本没变**都会判红；尚未 `git add` 的文件不在门禁范围内，门禁会把它们列出来提醒。
- 门禁通过后重建入库的生成页：`cd docs && node build-html-docs.mjs`（生成页不逐页登记，写进台账的批次说明即可）。
- 说明写清楚改动了什么规则、数字或示例。「优化文档」「同步更新」这类空话不算登记。
