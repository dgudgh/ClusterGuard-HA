# MySQL 灾难恢复的实际 binlog 可用性

## 修改前记录

本次任务是修复物理删除主库 binlog 后两从无法重建的灾难恢复功能。开始时唯一主线为 `codex/2.2-postgresql`，HEAD为`fa187f0`，工作树干净；现场三台产品版本为3.1.2.15。上轮正式现场复测失败，回执单独保留在本地版本目录，不把还原原日志后的收尾成功记作缺日志恢复通过。

修改前已读门禁执行流程、完整 `CG-UPGRADE-CONTRACT`、修改与证据规则、操作授权规则、后端恢复和交付入口。`contract_version=2`、`contract_loaded=true`。本次先完成SOURCE与隔离原生数据库回归；新补丁另执行ART，用户安装后才进行现场恢复验收。

## 历史对照与失败证据

- `c8795a3`首次引入的完整调用链为API/Manager计划与租约、全成员fencing、relay排空与原生证据、GTID选主、Runtime/DisasterExecutor重建、最终复制与Recovery Commit。
- `1931ecc..fa187f0`的`adapters/mysql/disaster_recovery.go`、`reparent.go`、Runtime Driver与relay排空无差异。旧实现使用`gtid_executed`和`gtid_purged`判断增量重连，仅`FastRejoinSafe=false`时克隆；它没有证明磁盘上的日志仍可读取。不能把这项长期缺口说成3.1.2.15新引入的回归。
- 真实冻结证据中，两从各缺14个源事务、无errant事务、purged缺口为0；现有纯GTID判据返回`FastRejoinSafe=true`。物理日志路径却已丢失，两从原生报source error1236，首次正式执行在重建从库阶段阻断。
- 原日志还原后，同一受保护任务正式重试成功。50个不同观测全部角色/节点/链路健康，但5个采样延迟1秒，严格50轮零延迟不通过。这项证据不因本轮源码修复而改写。

## 拟修改的边界

1. 选定主库仍保持冻结GTID与持久双只读；在有效恢复授权下建立并验证可读取的新binlog边界，保留旧日志和索引，不重置GTID。
2. 从库存在缺失事务时，除GTID集合外还检查实际源日志可读性。已证实的日志缺失使用已有受控克隆链；身份、授权、网络或权限证据不足继续阻断，不凭普通SQL错误执行破坏性重建。
3. 克隆使用已选定的权威主库，保留接收方身份、offline guard及受保护重启；失败也保持只读保护。最终GTID必须与冻结主库完全一致。
4. 复制等待超时时保留最近的原生IO/SQL错误，经过凭据清理和长度限制；不得被最后一次取消的查询覆盖。

不修改普通切换/旧主恢复的GTID决策、Manager租约、选择规则、维护冻结、writer lease及多数派语义。

收尾审查追加：既有克隆链在临时放开接收方super_read_only之后、实际CLONE之前没有再次调用授权和guard检查；大日志检查后的STOP及重配复制也需重新授权。开始这些局部修改前已核对旧调用位置，拟补逐步复核及“临时放开后撤权仍拒绝克隆并恢复只读”的行为回归，保持原恢复协议与失败保护。

## 验证计划

- 行为测试覆盖物理缺日志但purged不变、日志完整时增量重连、日志正常清理后克隆、完全相同GTID、errant/身份/授权/guard失败、日志查询权限失败、克隆失败保护及原生错误保留。
- 真实数据库回归使用独立新数据目录或全新隔离容器，复现日志路径删除、建立新日志、受控克隆、UUID保留、精确GTID与数据标记及后续复制。没有本机Docker时检查已有MySQL运行时，在专用回环端口和私人诊断目录内建立临时实例；不改变现场3306服务、数据目录或VIP。
- 新用例先在旧实现上证明失败，再实现。SOURCE严格门禁、失败变异、关联竞态、全仓Go/vet、语言/原恢复浏览器、Markdown/许可及生成页按实际结果登记。
- 新补丁使用新四段身份，旧3.1.2.15字节冻结。用户自己安装；本次不把隔离数据库回归说成三台现场验收。

## 原生依据

MySQL原生GTID自动定位从最新日志向前检查Previous GTID边界；物理克隆传递数据和GTID坐标，不复制binlog与relay文件。因此新复制边界必须可读，且克隆后仍须真实核对复制。依据：[GTID自动定位](https://dev.mysql.com/doc/refman/8.0/en/replication-gtids-auto-positioning.html)、[克隆用于复制](https://dev.mysql.com/doc/refman/8.0/en/clone-plugin-replication.html)。

## 当前状态

已在三个全新回环实例上复现旧实现失败：删除实际文件产生ERROR 29和OS errno 2，两从产生原生复制缺口，StartPrimary没有新日志边界。另发现MySQL在所有旧文件丢失后首次FLUSH可能复用文件名；其新Previous GTID头已经包含全部冻结事务，不能只凭文件存在就判定历史可用。实现需要检查实际Previous GTID边界，必要时再次旋转获得不同的活动文件名。初次夹具的48字符复制密码被MySQL拒绝，已改为32字符并另建全新夹具；该初次夹具失败不记为产品复现。
