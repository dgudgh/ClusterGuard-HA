# ClusterGuard HA 2.2-93：升级确认反馈修复

日期：2026-09-08。保持经典界面，未引入新的页面设计。

## 已确认的原因

在本地 Chrome 加载实际发布控制台代码，按选择文件、上传校验、生成计划、输入补丁 ID、确认升级的用户路径复现。API 和文件内容是隔离测试替身，不连接现场数据库，不代表现场验签或滚动升级验收。

1. `startSoftwareUpdate` 只更新通用升级区域，没有刷新确认框的按钮和文案。请求处理中内部变量已挡住重入，但按钮仍可点击，视觉上没有响应。
2. 原代码丢弃 POST 返回的任务，继续等待升级列表、版本、控制面三个接口全部返回，才关闭确认框。其中任何一个慢请求都会拖住已经受理的动作，而且原链路没有请求超时。
3. 提交错误写入已关闭的上传框及底层提示，最上面的确认框看不到错误。
4. 计划生成只等待 20 轮、每轮间隔 500ms，超出后要求再次点击。其轮询还重复等待上述三个接口。
5. 确认输入与提交目标读取当前列表第一项，而非打开确认框时的固定补丁，存在后台列表更新导致确认失配的风险。

这些是代码和本地浏览器已经验证的缺陷。未对现场当次请求抓包，不将具体现场时延归因于某个数据库或网络节点。

## 修复边界

- 确认后立即显示正在提交，并锁定确认、输入和关闭控件；执行、续跑、回退共用相同保护。
- 使用 POST 返回且已验证身份的任务立即打开进度框；版本、控制面状态独立读取，不阻塞任务受理反馈。
- 确认框内显示拒绝原因。POST 超时、网络断开、409、5xx 或无法确认的响应进入结果待确认状态；后续核对按钮只 GET 任务，不自动重发 POST。关闭重开也不会丢掉本页面的待确认状态。
- 固定本次确认的补丁 ID；提交前启动的旧快照不能覆盖刚受理或直接读取的新任务。
- 计划通过单包状态接口等待，超过旧约 10 秒窗口也会在就绪后自动打开二次确认。计划等待可以关闭；关闭不取消后台只读计划，也不自动升级。最多等待 5 分钟后明确报告计划未就绪。
- 保留手动输入补丁 ID、后台成功计划校验、权限、签名、Raft 多数派和维护门禁。没有放宽任何安全判定。
- 只修正确认弹窗的窄屏按钮布局和长补丁 ID 换行，其余经典 HTML/CSS 保持不变。

## 测试证据

- 改动前 4 个用户路径场景共 14 项断言，其中 6 项失败；保存在 `before/result.json`。
- 修复后 12 个场景、45 项断言通过，包括慢提交、慢辅助接口、拒绝提示、长时间计划、503、断网、30 秒超时、补丁变化、旧快照、取消等待、续跑和回退。
- 原有浏览器回归通过：12 次集群切换、24 个响应式页面视图、可切换标签、默认折叠日志、固定进度头和独立日志滚动。
- API 和升级管理器测试、race 检查及 Go 静态检查通过。全量 Go 测试首次因测试命令漏了 `/sbin`、找不到 `sha256sum` 而失败；纠正 PATH 后全量重跑通过，脚本测试耗时 238.563 秒。
- 两个包分别校验原始 91/92 回退 RPM、同一 93 目标 RPM、引导器、清单签名及全部 SHA-256；篡改清单被拒绝；实际升级脚本的只读 `--inspect` 通过。
- RPM 内嵌控制台与测试文件完全一致。与 92 比较，66 个非变更载荷文件保持一致；变动为 5 个带版本信息的二进制和 BUILD-INFO。

## 手动升级

目标版本为 `2.2-93`，架构为 `x86_64`。按当前实际运行版本二选一，不要连续上传两个包：

| 当前版本 | 上传包 |
| --- | --- |
| 2.2-91 | clusterguard-ha-2.2-91_to_2.2-93.x86_64.cgupgrade |
| 2.2-92 | clusterguard-ha-2.2-92_to_2.2-93.x86_64.cgupgrade |

91 到 93 的包同时包含 92 的轻量操作上下文读取修复，不需要先安装 92。其他来源版本不在这两个包的支持范围内。

仍从设置、版本更新、升级入口上传，保持现场安全检查。93 的确认交互是在升级完成并重新加载页面后生效；安装 93 这一轮仍由当前旧版页面发起，不能保证旧页面立即获得新交互，不要反复点击确认。

未自动安装、未 SSH、未替换现场公钥、未执行数据库恢复。未做现场真实文件上传验签及三节点滚动升级，本地结果不能代替现场验收。已有 92 发布包不覆盖。
