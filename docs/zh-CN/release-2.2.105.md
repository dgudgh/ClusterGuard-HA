# ClusterGuard HA 2.2-105 发布说明

## 本次变更

本版把 2.2-104 之后在现场暴露并修复的一批缺陷固化进正式介质。相对 2.2-104 的构建提交
`e01f5ce`，代码基线 `b383092` 含 27 个提交，按主题分为四组。**这些修复此前只以签名热修包
（`.cgpatch`）的形式在现场存在，没有进过任何安装介质**；本版是它们第一次随正式版本交付。

### 1. 集群时钟（本版主要变更）

- **修正集群时钟不再让集群进入停机态。** 修复前，把一台走时偏快的机器拨回真实时间，会把拓扑
  观测水位留在未来；此后每一次拓扑刷新都被"观测时间不在前一次之后"拒绝，拓扑永久不新鲜，
  VIP 归属租约不再续期，数据节点按设计摘掉 VIP 并把实例设为只读。**修正时钟这个动作本身会把
  集群推进停机态，且现场无法自解。** 现在超过任何合理排序误差的差距
  （`observationWatermarkRewindTolerance`，5 分钟）被当作"一口已不存在的时钟"：观测放行、
  水位落到新观测、严格顺序从该点重新生效；窗口内的顺序违规仍然拒绝，原有保护不变。
- 时钟回拨时重新锚定法定人数租约，避免租约在回拨瞬间被判失效。
- 隔离部署（无上游时间源）的时钟权威改为**显式选择**，控制台显示时区固定，不再由本机时间
  推导；集群时间配置增加门禁，安装时不再把未校验的本机时间静默升格为权威。
- `clusterguard-clock-mesh.sh` 改为随 RPM 交付（此前是 installer-only），现场可通过正常升级
  路径拿到修正后的副本，而不是长期停留在首次复制的那一份。

### 2. 写入者协调与整机重启可恢复性

- **停止 MySQL 写入者 reconcile 抖动。** 修复前主库每约 10 秒被节点 Agent 自我隔离一次
  （`read_only` 与 VIP 同步抖动），集群长期 degraded、复制链路反复 unhealthy、切换与关机预检
  被阻断。根因是收敛判据要求"重启后只读"这个永久站点不变量变为 false，而它按设计永远为真。
- 共享运行时目录保持可穿越，整机关机后重启不会再出现控制面与恢复单元连环重启的僵局。
- 主机断电时控制台页面自我收尾，不再停在一个已经消失的后端上。

### 3. 控制台

- **"不可用"的原因直接显示在面板与分区横幅上**，不必再靠推断；候选评估等环节被锁定时能直接
  读到服务端给出的判定输入。
- **「账户与偏好」并入「状态设置」**，功能页签回到三个。此前四个页签在常规宽度下换行，
  账户那一枚孤悬一行。账户与显示偏好成为状态面板内的一块，切到其他页签时随之离屏。

### 4. 在线升级与热修补丁通道

- **可从控制台「版本更新 → 上传升级包」安装签名补丁。** 控制器按 `kind=hotfix` 识别并交给
  更新 Helper 逐台应用，与滚动 `.cgupgrade` 走同一条上传接口但互不替代；补丁安装器自身也被签名。
- 更新 Helper 的 SSH 私钥由 root 持有（0600），运行时目录不再要求单元自有——修掉首次启动的
  目录竞态，同时避免停机删除共用目录。
- 跨基线的 `.cgpatch` 拒绝信息改为**明确命名陷阱**（"这个包属于别的基线，装上去会把二进制降级
  回它的发布线"），而不是含糊报错。

> 交付工具链本身（一次现场处理出一个累积补丁包、双语热修台账、相应防漏门禁）也在本版范围内，
> 但它不改变产品运行时行为，只影响我们如何把修复送到现场。

> **交付物不可变（2026-09-29 起为硬规则）**：已签名、已登记的 `.cgpatch` **永不原地重建**。同一个
> 文件名 + 同一个版本号 + 不同的字节，会让现场与仓库各说一套——现场报「我装的是 2.2-105」，仓库也
> 有「2.2-105」，而两边摘要不同，事后无法证明节点实际运行过什么。任何修订都必须产生**新身份**：
> 文件名带 `-r1`，manifest 带 `revision` 与 `supersedes_artifact{file,sha256,reason}`。构建脚本现在
> **拒绝**覆盖任何已存在的产物；台账 `hotfixes/hotfix-publications.json` 是身份的唯一真源，门禁逐条
> 核对已登记摘要是否与磁盘逐字节一致、修订是否指回被替代的身份、同一交付线是否只有一个 `current`
> 入口、以及有没有哪条声明指向了已被取代的修订。已经是证据的旧身份不回炉：它的字节不按
> 今天的规则升级，而是把仍带的缺陷逐条写进台账（`status: frozen` + `known_defects`），门禁对这份声明
> 做**双向**校验——既不许少声明，也不许声明一个已经不存在了的缺陷。
>
> 台账放在**源码树**（`hotfixes/`）而不是介质树：`release/` 从未被 git 跟踪，一份只存在于某台机器上
> 的来源记录不算记录。条目按「相对介质根的路径」索引，于是台账随分支传播、产物留在原地。
>
> **分工：签名清单只写"为什么替换"，实测数据写台账。** 清单里的 `supersedes_artifact.reason` 一旦
> 签名就不可改写，所以不放任何会随时间漂移的事实、路径或量化断言——否则一个笔误就要再出一个几乎
> 相同的交付物来纠正。这一条是踩出来的，见下节。

## 一次自己犯下的发布事故，与它逼出来的四条规则

`release/2.2-103-hotfixes/` 下的 `HF-2026-0928-02` 从 r0 一路走到 r4，五个身份全部保留在台账里。
过程本身是本版最有价值的产物——它把"不可变"从一句口号变成了可执行的判据：

| 身份 | 摘要前缀 | 状态 | 发生了什么 |
|---|---|---|---|
| r0 | `71083a21…` | superseded | 17:47 被一次**同名原地重建**覆盖，三个现场节点都没有 2.2-103 线的包，无法取回。字节已丢失，摘要保留为唯一记录 |
| r1 | `62bc8c7c…` | superseded | 以新身份重建以恢复该线可交付性。缺陷：签名清单把台账位置写成 `release/hotfix-publications.json`，而台账随后迁入源码树，指针失效 |
| r2 | `4cf15ee1…` | superseded | 为纠正 r1 的指针而构建，却在理由里写下未经实测的断言「载荷与 r1 逐字节相同」——不成立 |
| r3 | `13731cae…` | superseded | 纠正 r2，但把差异字节数写死成「每个二进制 63 字节」。实测三个身份两两之间：`clusterguard` 63/61/63 字节、`clusterguard-agent` 40/40/40 字节 |
| r4 | `b11c939f…` | **current** | 该线当前入口。理由里不再有任何量化断言 |

四条规则：

1. **已签名即不可变。** r1 到 r4 的每一次纠正都是新身份，没有一次回去改写旧字节。构建脚本在写出
   产物前检查路径是否已存在，存在就**拒绝**并把操作者引向新身份。
2. **签名清单里不放会漂移的断言。** r2、r3 的两次返工都源于此——不是算错，而是把不可修订的位置
   用来承载可修订的内容。清单只保留"为什么替换前一个身份"。
3. **产物二进制不可复现，所以台账摘要不可替代。** 同一 `build_commit` 两次构建得到**大小相同、
   代码相同**的二进制，但每个二进制有几十字节不同，那差异全部落在 Go 的 build ID 上（由构建路径
   派生）。因此"重新构建一次对拍"**不能**用来判断一份产物是否被换过——唯一可信的比对基准是本台账
   登记的摘要。这是一条已知限制，不是本次文案修订的产物。
4. **门禁要理解 `frozen` 与 `superseded` 的区别。** 修订保留在介质目录里是**正常且必要**的——那些
   字节是"现场到底运行过什么"的证据。所以"这个目录里只有一个 `.cgpatch`"不再是正确的不变量；
   正确的不变量是"这个目录里最多只有一个 `current`"以及"没有哪条声明指向已被取代的修订"。按文件
   数做判据会在第一个修订出现时变红，而真正的歧义（两个 `current`）反而漏过去。

## 介质构建之后发现的缺陷：升级弹窗里点不动的两个动作

本版介质打包提交是 `bf2feeb`，打包完成于 2026-09-29T04:48:28Z。**介质构建之后**，现场在同一天
（2026-09-29）的两轮控制台实操里暴露出五个缺陷，因此**本介质里仍然带着它们**，修复不在介质内。

这五个缺陷是同一句话的两次现身：控制台判断「这个包能不能装在本集群上」时只读了时间轴——记录新不新、
作业失败过没有——没有读另一个维度：**包与集群的关系**，也就是包的 `source_version` 与集群正在跑的
发布线是否一致。这一维上算错的代价很实在：唯一能执行的那个包被一个永远装不上的包挡住，而页面上
没有一句话说明原因。

### 第一次（13:16）：首行是一条时间戳落在未来的终态记录

- 现象：上传 `.cgupgrade` 后校验通过、历史记录出现「已上传」，但「滚动升级」按钮始终灰着点
  不动；同一个对话框上方却是绿色的「校验完成」，页面不解释原因。
- 根因：控制台把「待升级目标」与「滚动升级」按钮都锚在升级记录的第一条上，而排序键
  `uploaded_at` 同时就是要显示给操作员的那一行。一旦首行是一条**时间戳落在未来**的记录
  （某台控制节点走时偏快时写入的），它就永远排在最新上传的包之上；该记录带终态任务，于是
  「待升级目标」解算为空、按钮被禁用，而校验面板只看上传结果，仍在报「校验完成」——同一界面
  的两半互相矛盾。
- 修复（两个提交）：控制台改为按「最新仍可执行的记录」定位主体，身份栏、三个按钮闸门、只读
  计划与确认框都从同一主体推导，并在无包可执行时改说「校验完成，但当前没有可执行的升级包」
  且点名占住列表的那条记录；服务端在 `PackageStatus` 上增加 `clock_skew`（容忍 5 分钟），
  让历史行自己标注「记录时间戳晚于当前时间，排序与时间不可信」。
### 第二次（14:02）：一个属于别的发布线的包占住了唯一可执行槽

- 现象：为了给 2.2-105 备好修复，现场把一个**属于 2.2-105 发布线**的热修补丁
  （`HF-2026-0929-04`，`source_version = 2.2-105`）上传到**仍停在 2.2-104** 的集群。上传顺利、
  记录随即出现并占住控制台**唯一的可执行槽**；点「计划」后升级器按设计拒绝，但真正该执行的
  `cgupgrade-2.2-104-to-2.2-105-x86_64` 排在被它压住的位置，从界面上无法选中。于是集群的升级
  通道被一个本机永远装不上的包堵死，且当时没有任何退场手段：该版本没有删除或停用记录的接口，
  而重传同一份内容会返回既有记录并保留原始 `UploadedAt`。
- 根因：三个各自都正确的设计叠在同一处。① 上传口只回答「这个包是不是我们的」（验签），不回答
  「这台机器能不能装它」；② 列表按 `uploaded_at` 倒序、列表项只认第一条、且对话框里没有包选择器；
  ③ `failed` 是**可重试**状态，所以失败记录不退位。唯一正确的拒绝来自升级器自己的基线校验，
  而它排在最后，结论也不回流到任何一条已经做出的判定里。
- 修复（三个提交）：① 上传口改用**升级器自己的口径**拒绝跨基线包
  （`ErrPackageBaselineMismatch` → HTTP 409），且拒绝发生在建立目标目录**之前**，被拒的包连记录
  都不留下；`Snapshot` 同时给已有记录打上 `incompatible` / `incompatible_reason`，把同一句判定
  带给前台。② 控制台把 `incompatible` 记录排除出可执行候选，历史行标注它属于哪条发布线、
  本集群是哪条；一条可执行记录都没有时改说「当前没有可执行的升级包」并点名那条跨基线记录，
  而不再说「已经执行完成，不能重复发起」。③ 失败作业从升级器写进 `output.log` 的
  「升级失败：…」里提取真实原因交给操作员，不再指向这条路径上根本不存在的「维护门禁」。

  `release/2.2-105-hotfixes/clusterguard-ha-hotfix-HF-2026-0929-04-2.2-105.x86_64.cgpatch`

## 热修通道自身的失败路径：一次失败之后再无自动出路（16:22）

上面五个缺陷修完并打成 `HF-2026-0929-04` 之后，现场当天又做了第二轮实操：**滚动升级到 2.2-105
成功**（16:03 记录 `succeeded`，维护门禁随之释放），随后操作手**再次上传并执行同一个热修包**。
这一次它失败了，而且在失败之后**把自己锁死**——现场没有任何一条自动路径可以走。

- 现象：逐台应用看起来正常，随后在 `.154` 上报 `hotfix failed; automatic rollback started`，
  `status.json` 停在 `failed` / `phase: rollback` / `current: 0`；日志里的判据是 `leader_changed`
  （60 秒等待超时），而三台 `clusterguard-ha` 都在 16:23 前后重启过一次——那正是本次应用自己做的。
  此后控制台横幅显示「升级维护未闭环 · 维护门禁仍生效 / 自动故障切换已暂停」，而对话框给出的两条
  建议（续跑 / 回退）撞在同一个走不通的动作上。
- 根因（三条串成一条链）：① 热修按 `ordered_nodes` 逐台应用、Leader 刻意排最后，而每台应用完都执行
  `wait_cluster_idle "${leader_host}" true idle`——把**应用开始前**解析出来的那台 Leader 当成必须不变
  的期望；被重启的最后一台恰恰就是它，重新选举使 `observed_leader` 改变，于是这个等待在**刚刚成功**
  的路径上必然超时。② 判失败后走自动回退，而生成的 `rollback.sh` 用 `cp` **就地覆盖**目标文件；被
  替换的文件里包含正在运行的 `/usr/local/bin/clusterguard` 与 `clusterguard-update-helper`，就地写入
  必然 `ETXTBSY`（应用这一侧从不失败，是因为 `apply.sh` 用的 GNU `install` 会先 unlink 再创建），
  于是三台回退全部失败。③ 回退失败的设计后果是保留维护门禁，而门禁只能靠「重跑同一个补丁」接管——
  可热修分支在调用 `detect_current_update_lock` 之前就 `exit` 了，接管分支永远不可达，重跑又被
  「必须没有维护态」这条准入检查拒绝。三条合起来：**继续走不通，退回去也走不通**。
- 处置：只能人工解封——备份 `updates/` 下的作业记录、在 Leader（`.153`）上调 `gate/release`、三台
  改名移走 `.cluster-update.lock` 与 `/etc/clusterguard/update-maintenance.json`。
- 附带修掉的第四条缺陷（同源）：`rollback.sh` 取「最新的」`backup-*.txt` 而不是本补丁自己的清单，而
  `restore_backup()` 把「清单里没有这条记录」解释成「补丁前不存在」并直接 `rm -f` 目标——取错清单会
  **删掉在役的系统文件**。现在备份清单名带上补丁编号，回退只认本补丁的清单。

### 交付形式与顺序约束（HF-2026-0929-05）

- 交付形式：签名热修包
  `release/2.2-105-hotfixes/clusterguard-ha-hotfix-HF-2026-0929-05-2.2-105.x86_64.cgpatch`
  （96,054 字节，sha256 `259c2364…`）——**一个包**覆盖上述四个缺陷。

> **本包不含任何二进制，因此应用过程不重启任何服务。** 这不是省事，而是它成立的前提：本包修的正是
> 「热修重启节点会把流程自己打翻」，而执行安装的仍然是现场那份旧脚本，只有让本次应用根本不重启，
> 修复才能在被那个缺陷踩到之前先装上去。安装之后，**下一次**热修（以及任何会重启节点的包）才真正
> 受这条修复保护。
>
> **它是 `HF-2026-0929-04` 的增量，不取代它**：`base_commit` 就是 HF-04 的构建树（`d2e5d85`），
> 现场三台已经跑着 HF-04 的载荷（`/usr/local/bin/clusterguard` 三台同为 `26cf134f…`、
> `--version-json` 报 `2.2/105/d2e5d85`），所以现在只需要上传本包。反过来，本包也不能脱开 HF-04
> 单独使用。

### 现场验收口径（本包起生效）

- **验收对象是 `/usr/local/sbin/clusterguard-upgrade`，不是 `/usr/local/bin/clusterguard`**——本包根本

## 使用入口

```bash
sha256sum -c clusterguard-ha-2.2-105-offline-linux-x86_64.tar.gz.sha256
tar -xzf clusterguard-ha-2.2-105-offline-linux-x86_64.tar.gz
cd clusterguard-ha-2.2-105-offline-linux-x86_64
sha256sum -c SHA256SUMS
bash install_clusterguard.sh --help
```

安装器默认只生成计划，显式 `--execute` 才修改主机。首次登录前先取得初始口令：部署设置了
`bootstrap_admin_password_env` 时用该值；未设置时读取控制节点上 `<metadata_path>` 同目录的
`bootstrap-admin-password`（0600，仅 root 可读）。安装器在交互终端下会先从 Leader 读回真实口令
再显示，不打印固定口令。

**已有集群不要用新装命令覆盖部署状态、Raft 数据、数据库目录或身份文件。** 本压缩包不能上传到
升级弹窗；现场升级请使用对应来源版本的签名 `.cgupgrade`（本版为
`clusterguard-ha-2.2-104_to_2.2-105.x86_64.cgupgrade`）。
