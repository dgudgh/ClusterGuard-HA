# 迁移高可用工具时，别让两个控制器同时能切

从 Orchestrator 或 MHA 迁移到新的高可用平台时，最容易被低估的是中间阶段。

旧系统还在监控和自动恢复，新系统也已经发现拓扑、安装 Agent、准备接管 VIP。两边页面都显示健康，看起来多了一层保险。

风险就在这里。

主库失效以后，两套控制器可能同时行动，选择不同候选，分别修改复制源，再去争夺同一个 VIP。任何一套系统单独测试都没有问题，组合以后却失去了唯一执行者。

## 只读观察可以并行

先只读。

迁移初期，两套系统可以同时读取数据库状态。

ClusterGuard HA 先以控制面方式部署，登记现有实例，并依据 MySQL `server_uuid` 建立资源身份。运维人员对比两边看到的主库、副本、GTID、延迟、线程状态和候选排序。

这段观察期很有用。它能发现主机名别名、端口变化、清单遗漏和候选规则差异，也不会改变现有数据库。

切权只有一次。观察期间，新平台不能拥有恢复和 VIP 变更权。

## 正式切权要有维护窗口

进入切权窗口以后，先停止旧系统的自动恢复，再处理所有周边入口。

需要检查 Orchestrator recovery、MHA Manager、VIP Hook、Keepalived、timer、cron 和人工守护脚本，现场还要证明旧系统已经无法提升主库、修改复制源或漂移 VIP；ClusterGuard HA 随后接管 Agent 与 VIP，完成一次人工受控切换，验证新主、旧主、其他副本和 VIP 以后，再把旧主恢复到当前复制关系。

数据库通常不需要重装。现有数据和复制关系可以继续使用，变化集中在资源登记、控制权和端点管理。

## 回退也要保持唯一变更权

迁移失败时，不能直接重新启动旧控制器。

先停止 ClusterGuard HA 的自动恢复与端点变更，确认没有运行中的操作、操作锁和有效 VIP 租约。随后按回退计划恢复旧系统，并重新验证唯一主库和唯一入口。

整个过程里，同一套数据库始终只能有一个系统拥有变更权。只读发现可以重叠，写入控制不能重叠。

迁移高可用平台时，控制权怎样交出去、失败以后怎样安全拿回来，需要在导入配置之前就写清楚。
