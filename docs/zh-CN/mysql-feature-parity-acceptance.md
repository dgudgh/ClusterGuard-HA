## 验收结果

- 六个集群的基线烟雾检查通过。
- 完成了二十次轮询和三十次随机真实切换：`50/50`。
- 主节点分布在节点上，且在并发活动期间，不同的集群 VIP 保持隔离。
- Leader 控制器失联后完成了重新选举，所有控制器快照最终一致。
- 控制器丢失多数派后按失败时阻断策略收敛：全部 18 个实例变为只读，六个 VIP 全部移除。多数派恢复后系统自动重新收敛。
- 一次真实的主节点网络分区在大约 55 秒后触发了 8.0 故障转移。新的主节点拥有唯一的 VIP，所有副本都跟随它。
- 恢复后的旧主通过增量方式重新加入，并持续保持只读。
- `192.168.102.154` 的完全重启恢复了控制器、代理和协调计时器服务；六个集群的健康状态和 VIP 唯一性恢复。
- 重复的恢复主节点 MySQL 重启没有创建写主或 VIP 冲突。
- 跨节点重建重用了原始平台 UUID 和固定节点名称。故意注入的目标专用模式在捐赠者导入之前被删除；GTID 集在两个方向上匹配，复制线程正在运行，延迟为零，重建的副本上没有剩余的 VIP。
- 实际的主机名、IP 和 MySQL 端口被更改并协调，然后恢复。相同的资源 UUID 和 `server_uuid` 保持不变；旧端点成为别名，没有创建重复的节点。
- 所有三个控制器上的最终拓扑快照相同，清理后所有六个集群的烟雾检查都通过。
- 控制台全局概览、紧凑拓扑、操作工作台、节点生命周期、指标、可搜索操作日志、设置和元数据对话框是针对实时的三个控制器 API 而非固定数据进行的。
- 通过浏览器驱动的真实切换完成了所有五个可见阶段：预检查、计划、安全门、执行和验证。直到持久操作达到 `succeeded/report` 并通过验证后，结果才被声明为成功。
- 在一次真实切换期间重现了短暂的写后读陈旧窗口，被回归测试覆盖并修复。控制台现在在渲染验证结果之前等待预期的主节点，而不是用瞬时的从节点快照替换它。
- 在第二次真实切换后，观察到 40 秒的只读自动刷新。验证结果、五个完成的阶段、选定的集群和新主节点在 30 秒的刷新间隔内保持不变。
- 发送到从节点的变更操作失败并返回当前的 Leader API 地址。相同的操作在 Leader 上执行并记录为操作 `fd5e2277-efe0-46bb-b690-c55da3935783`。
- 清理后，每个控制器都报告 `orch-mysql03` 在 `192.168.102.154:3306` 上为 `mysql-ha-3306` 的唯一主节点；只有该主机拥有 VIP `192.168.102.155`，最新的操作仍被验证。

## 本地验证

```bash
gofmt -w $(rg --files -g '*.go')

```

配置 JSON、shell 语法、洁净室命名、依赖卫生、包内容和清单检查也是最终发布门的一部分。

实时实验室根目录提供了预期的 `ClusterGuard HA Console` 标题、中文默认语言和六个集群的 API 目录。浏览器自动化通过仅环回的 TLS 终止测试桥接至活动控制器执行；它不会更改实验室服务器或生产网络路径。视觉检查覆盖了概览、拓扑、操作工作台、节点、指标、日志、设置、关于页面和元数据对话框。操作日志确认显示本地时间、稳定的集群名称、源节点和目标节点、状态以及一个可按需展开的原始工作流对象。

## 平台认证和一次性审批更新

2026-07-16 授权更新添加了 Raft 复制的平台用户和会话，同时保留仅哈希、一次性操作授权：

- 新的元数据存储引导 `admin`，使用文档中 `admin123` 的首次登录密码和 `MustChangePassword=true`；

> **2026-09-22 已被取代：** 以下条目记录的是 2026-07-16 那次更新交付时的行为，
> 当时首次登录密码固定为 `admin123`。现在平台在部署设置了
> `bootstrap_admin_password_env` 时取该变量的值，否则由 Leader 生成并写入与元数据
> 同目录的 root 专属文件 `bootstrap-admin-password`。本验收记录的其余部分不变。
- 在任何数据库或管理变更操作被接受之前，首次密码更改是强制性的；
- 密码使用 Argon2id，浏览器会话有八小时的绝对生命周期，密码更改或注销会撤销活动会话；
- 会话认证的 `admin` 和 `operator` 执行构建精确的持久操作计划，在服务器内创建一次性授权，原子地在 `APPROVE` 消耗它，并且从不将审批密钥发送到浏览器；
- 显式服务自动化保持独立：控制 Bearer 认证客户端，一次返回一个明文授权，授权保持绑定到集群、引擎、操作类型、目标、观察和计划；
- 已消耗、过期、不匹配、重放和陈旧计划的授权失败时阻断；
- HA 矩阵支持与浏览器等效的平台会话执行，并保留一个独立的显式授权模式用于服务客户端重放测试；
- 自动故障转移使用私有事件授权路径和无人工令牌，同时保留多数派、隔离、锁定、验证、审计和报告。

本地 API 验证覆盖了引导登录、密码更改前的变更操作阻塞、会话撤销、重新登录、CSRF 保护的读写和清理后的响应。

认证控制路径在 2026-07-17 CST 完成了新的三主机破坏性验收：

- 分支 `codex/platform-auth-session`，工作流修复提交 `545c44c` 和 `4b5e5df`；
- 发布归档
  `clusterguard-ha-platform-auth-rc4-linux-amd64.tar.gz`，SHA-256
  `ac97e44af9727c45214bb5c4e793aa30bc40feaf509250f2ece3a25304ee3dfc`；
- 在允许业务 API 访问之前临时引导密码已更改；旧会话被撤销，重新登录成功，注销撤销其会话，未认证的业务读取返回 `401`；
- 专用监控 Bearer 保持 GET 仅，滚动升级后所有三个控制器都返回 `200`；
- 第一次真实会话切换暴露了一个工作流缺陷：周期性发现提前了元数据修订，但未更改语义拓扑摘要，而执行重建了一个已审批的不可变计划并拒绝了其新的摘要；
- 回归测试
  `TestDurableWorkflowReusesPersistedPlanWhenOnlyMetadataRevisionsAdvance`
  在修复前重现了缺陷，并在执行改为重用确切的持久计划后通过，同时保留当前的预检查、安全、锁定、拓扑重新验证、审批、验证、审计和报告门；
- 回归测试
  `TestPutDurablePlanPreservesOperationIdentityOnPersistenceFailure` 也

- 操作 `92ec6cda-c2b6-4fbb-aca5-27c1848aa29a` 然后通过
  `succeeded/report` 验证通过，将 `mysql-ha-3306` 从
  `192.168.102.154:3306` 移动到 `192.168.102.152:3306`；
- VIP `192.168.102.155` 仅存在于新主节点上。`192.168.102.153:3306` 和旧主节点
  `192.168.102.154:3306` 都是只读的，跟随
  `192.168.102.152:3306`，两个复制线程都在运行，并报告零延迟；

- 终端操作和已消耗的授权在所有三个控制器的元数据副本上都存在。

`15c6ec6b62f52b775b69f3a66a15937420f555f9f15f5578c30ad19f47e98f79`。

## 仍需生产资格

- ClusterGuard 自我隔离和多数派门禁存在，但生产必须集成一个独立的带外隔离机制用于失败的主机。
- 接受的重建使用了逻辑转储回退。克隆和版本匹配的 XtraBackup 助手必须在生产中选择之前进行资格认证。
- 备份保留、灾难恢复、外部警报传递和长期指标保留仍然是部署责任。
- 破坏性矩阵必须在目标硬件、存储、网络、操作系统和确切的 MySQL 包上重复。
