# ClusterGuard HA 2.2-72：节点服务恢复与失败升级接管

构建日期：2026-09-07。来源版本：2.2-68。架构：Linux x86_64。

## 现场问题

2.2-71 的真实滚动执行在首个混合节点安装目标 RPM 后未通过服务就绪检查。升级器只显示 `node update failed`，没有指出 RPM、控制面、Agent 或 Reconcile Timer 中哪一项失败；自动回退重新安装 2.2-68 后又被同一检查阻断，维护门禁因此保持关闭。

## 修复

1. 计划与执行都输出每个节点的 RPM、`clusterguard-ha`、Update Helper、Agent 和 Reconcile Timer 的 active/enabled 状态，不包含凭据。
2. RPM 事务后显式恢复并验证角色所需的 systemd 单元：控制节点启用 HA，非 Leader 控制节点重启 Helper，数据节点启用 Agent 和 Reconcile Timer。
3. Leader 上正在承载升级任务的 Helper 不在事务中重启，只保证开机启用；任务终态持久化后再异步刷新。
4. 节点就绪等待使用 90 秒真实墙钟上限，SSH 与 API 探测时间计入预算；超时时输出版本、控制面摘要和 systemd 状态。
5. 新包只在旧升级已经终态失败、三节点锁和维护标记完全一致、所有节点均已回到源版本时接管旧维护门禁。接管失败会补偿回原锁，不安装 RPM。
6. 去除 Helper 受保护运行环境中重复的 `/root/.ssh` 创建警告，不改变已审核 known_hosts 和 SSH 身份限制。
7. 升级维护期间允许管理员上传验签新包并运行只读计划；执行仍需计划成功、补丁 ID 二次确认，并由升级器完成旧失败锁接管校验。其他平台写操作继续被维护门禁阻断。
8. 同一补丁的续跑使用独立执行 ID，检查上一轮持久化事件确已进入失败终态；回滚期间保持运行状态，禁止同时续升。接管、RPM 事务和解锁使用主机级互斥锁，变更前校验执行所有者。
9. 本地维护标记与 Raft 维护记录共同生效。全部节点支持新门禁能力后，先建立 Raft 门禁，再逐台删除本地标记，最后由当前 Leader 原子释放 Raft 门禁。中途选举不会提前开放自动变更。
10. 升级协议仍兼容版本 1；二进制通过 `update_gate_protocol=1` 显式声明门禁能力。回退到不支持该能力的旧版本时保留本地门禁，并报告待恢复状态，不能伪报维护已释放。
11. 异常退出补写执行终态；仅剩 Raft 门禁时，Helper 仍保持维护状态，避免界面误报自动切换已恢复。

## 发行状态

2.2-71 已在真实三节点执行中失败，不能作为已验收版本。2.2-72 只有完成下述 Chrome 全流程和独立节点核验后，才能标记为现场验收通过；仅有单元测试、签名检查、上传成功或只读计划均不构成验收。

## 验收要求

必须通过真实 Chrome 完成上传、验签、只读计划、补丁 ID 二次确认和三节点滚动执行。验收需同时证明：

- 三个节点 RPM 均为 2.2-72。
- HA、Update Helper、Agent 和 Reconcile Timer 符合节点角色且 active/enabled。
- Raft Leader、3 节点多数派与元数据提交正常。
- 升级维护门禁已释放，自动故障切换恢复。
- MySQL 与 PostgreSQL 拓扑、复制链路和健康状态通过连续检查。

## 现场恢复约束

旧 2.2-68 会把失败维护状态下的上传入口一起锁住。必要时仅用已验证签名包中的控制面程序临时恢复升级入口，保留三节点维护标记与全部数据库状态。该引导步骤必须单独记录，不计作浏览器升级验收。随后重新通过 Chrome 上传最终包、生成计划、输入补丁 ID 并执行完整三节点滚动流程；完成后撤销临时入口配置并检查正式 systemd 程序路径。
