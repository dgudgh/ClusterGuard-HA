# 改个主机名，数据库怎么就多了一台

一台 MySQL 没有重装，数据也没有搬家，只改了主机名。

高可用平台一刷新，节点重复了。

旧主机名和新主机名同时出现在拓扑里，两条记录甚至可能进入同一份候选列表；运维人员以为自己选了另一台从库，后台实际指向的仍是原来的数据库实例。

这类问题看起来像页面没有清理干净，实际会影响切换安全。

## 主机名不能承担永久身份

很多管理工具用 `hostname:port` 识别数据库。连接很方便，身份却不稳定，因为两项信息都会变化。

主机名会因规范调整而修改，IP 会因迁移而变化，数据库也可能换端口。如果每次变化都创建一条新记录，同一个实例会在平台里留下多个身份。旧记录继续参与健康检查和候选选择，串节点、重复节点和错误操作对象就会出现。

MySQL 自己已经提供了更稳定的线索，也就是 `server_uuid`。

ClusterGuard HA 为平台资源分配不可变的 `resource_id`，再用 `server_uuid` 识别 MySQL 实例。主机名、IP 和端口只作为可修改 endpoint。平台在新地址发现同一个 `server_uuid` 时，会更新当前 endpoint，并把旧地址放进 aliases，原来的资源身份保持不变。

```text
resource_id        永久平台身份
server_uuid        MySQL 原生身份
hostname / IP      当前连接地址
port               当前实例端口
aliases            历史地址
```

这几个字段分开以后，改主机名不会制造新节点，历史审计也还能还原旧地址。

## 发现也不能越过集群清单

身份稳定以后，还要解决另一种串节点。

假设同一批服务器运行两套 MySQL，端口分别是 3306 和 3307。发现逻辑如果只凭主机可达就继续探测，很容易把另一套实例带进当前集群。候选下拉框随后会出现不属于这套复制关系的节点。

ClusterGuard HA 让每个集群维护一份权威实例清单。发现任务只能读取清单内 endpoint，所有控制操作也只能指向清单内的 `resource_id`。新增、退役和修正节点都要先修改元数据，再重新完成发现。

严格清单会多一道管理步骤。它换来的是一个更重要的保证，页面里出现的候选节点确实属于当前集群。

## 页面应该承认自己不知道

还有一种常见误判。数据库已经停止，平台却继续用上一次快照画出“副本健康”。

ClusterGuard HA 的拓扑页面只展示当前探测能证明的事实。实例无法连接时显示不可达，角色无法确认时显示未知。旧快照可以留给审计和排障，不能填充成当前状态。

这一点没有让页面更漂亮，却让操作员知道哪些信息还能用于切换判断。

高可用平台的第一项能力，往往不是提升主库。它要先认对节点，并且在地址变化以后仍然认得同一个数据库。
