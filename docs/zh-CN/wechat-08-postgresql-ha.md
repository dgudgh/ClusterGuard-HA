# PostgreSQL 接进来了，ClusterGuard HA 2.2 做到了什么

ClusterGuard HA 2.1.45 封板时，公众号系列对产品边界写得很克制。正式交付的是 MySQL，PostgreSQL 还处在 2.2 开发与验收阶段。

现在这段话可以更新了。

ClusterGuard HA 2.2 已经完成 PostgreSQL 原生高可用功能，并在三节点 PostgreSQL 16.4 环境跑完一轮实验室验收。这里说的支持，包含实例发现、身份绑定、拓扑与健康、候选评估、计划切换、自动故障切换、写 VIP、旧主恢复、Raft 多数派保护、审计和报告。它直接管理 PostgreSQL 流复制，不依赖 Patroni、repmgr 或其他数据库控制器。

这仍是一条候选版本线。通过实验室矩阵，说明核心流程已经成立。进入客户生产环境之前，还要按现场数据库构建、操作系统、网络、存储、客户端和隔离条件复测。

## PostgreSQL 不能照搬 MySQL 的切换命令

把一个 MySQL 高可用产品改到 PostgreSQL，最省事的做法是换几条命令，再把页面上的端口从 3306 改成 5432。这样的实现经不起故障测试。

两个数据库对身份、复制位置、角色和旧主恢复的表达都不同。

MySQL 用 `server_uuid` 识别实例。PostgreSQL 集群则用 `system_identifier` 确认数据库身份，每个物理节点再绑定 ClusterGuard HA 分配的不可变 `resource_id`。主机名、IP 和端口仍然只是端点。地址变化以后，平台更新当前端点并保留旧别名，不会把同一个节点登记两次。

候选评估也不能只看端口是否存活。PostgreSQL Adapter 会检查恢复状态、WAL 接收与重放、上游身份、时间线、延迟和观测新鲜度。证据不足的节点不会被排到候选首位。`system_identifier` 不一致、重放暂停、时间线不兼容或拓扑已经过期时，切换会在预检查阶段被阻断。

这些数据库差异留在 Adapter 内。Safety Guard、操作锁、一次性授权、Raft 多数派、执行后验证、审计和报告仍由统一控制内核负责。

## 一次计划切换怎样完成

计划切换开始前，控制器重新发现主库和两个备库，固定源节点、目标节点、WAL 状态、写入口和集群清单代次。操作取得集群级锁以后，候选状态被再次复核。

执行阶段会限制旧主的新写入，收敛 WAL，停止并证明旧主已经退出写角色，随后提升目标备库。其余备库改为跟随新主，写 VIP 移到新的可写节点。最后一轮发现必须同时证明下面几件事。

- 集群只有一个可写主库
- 写 VIP 只有一个所有者
- VIP 所有者就是当前主库
- 其余节点以流复制备库运行
- 操作中的目标身份与最终主库一致

任何一项没有得到完整证据，操作都会进入需要验证的状态。命令执行过，不能直接等同于高可用切换完成。

## 自动故障切换为什么更严格

自动接管面对的难题，是旧主可能仍在另一段网络里运行。数据库连接超时只能说明当前探测失败，不能证明旧主已经失去写入能力。

本轮 PostgreSQL 候选配置要求连续三次失败观测，并且证据跨度不少于三秒。达到故障窗口以后，控制器还要确认自己是当前 Raft Leader，并且仍然拥有多数派授权。旧主隔离需要由受限 Agent 或现场外部隔离能力给出可验证结果。多数派丢失、隔离无法证明或候选状态过期时，系统停止变更。

数据节点上的 Agent 也持续检查自己的授权。节点失去当前多数派授权后，会撤销本机 VIP，并停止继续承担写节点职责。这个十五秒宽限用于防止网络抖动造成误动作，同时给少数分区里的旧主设置明确失权边界。

## 旧主回来以后怎样处理

新主接管完成，只完成了事故的前半程。

旧主恢复时，它可能只缺少一段 WAL，也可能已经落在另一条时间线上。ClusterGuard HA 会先检查系统身份、时间线和 `pg_rewind` 前提条件。满足条件时，旧主通过受控 `pg_rewind` 修正数据目录，再以备库身份启动并追平。无法安全 rewind 时，平台阻断这条捷径，转入 `pg_basebackup` 全量重建流程。

恢复任务完成前，系统还会验证目标节点保持只读、上游身份正确、流复制已经建立，并且目标节点没有持有写 VIP。旧主能启动，只能说明进程活着，不能说明它已经安全回到集群。

## 这轮三节点测试跑出了什么结果

实验室使用 `192.168.102.152`、`192.168.102.153` 和 `192.168.102.154` 三台服务器。数据库为 PostgreSQL 16.4，端口 5432，集群名为 `pg16-ha`，写 VIP 为 `192.168.102.155/24`。三台机器同时运行 Raft voter 和受限 Agent。

| 场景 | 实测结果 |
| --- | --- |
| 身份与拓扑 | 一个 `system_identifier`，三个不可变节点 ID，一个主库和两个流复制备库 |
| 计划切换 | 首次约 8 秒，随后在三节点间连续轮换 5 次，每次约 10 秒 |
| 并发切换 | 一个请求完成，另一个被操作锁和拓扑复核阻断，只发生一次角色变化 |
| 主库虚拟机强制断电 | 写入口中断 15.1 秒，从断电标记到首次写成功约 24.97 秒 |
| 主库网络分区 | 客户端设置 `connect_timeout=2` 时，写入口中断 17.973 秒 |
| 控制面失去多数派 | 变更权限关闭，隔离节点撤销 VIP 并退出写角色 |
| Raft Leader 重启 | 新 Leader 正常选出，数据库主库、VIP 和数据保持稳定 |
| 旧主恢复 | 完成受控 `pg_rewind`，旧主以流复制备库回挂并追平 |

测试结束后，三台数据库的验证表均为 3512 行。`192.168.102.154` 是唯一可写主库和唯一 VIP 所有者，另外两个节点均为 streaming 备库。整个矩阵没有出现双主或双 VIP。

这些时间是本轮环境的观测结果，不是面向所有现场的固定 SLA。

## 客户端超时会直接改变用户感受到的 RTO

同一轮网络分区测试还暴露了一个经常被忽略的问题。

控制面已经完成接管，不代表应用会立刻恢复。如果客户端连接没有设置有界超时，一次旧连接可能继续等待。本轮有一条未限制连接超时的调用等待了约 31.97 秒，明显长于控制面实际完成切换的时间。

因此，生产验收要从旧写请求失败开始，一直测到新写入口首次提交成功。客户端需要设置合理的连接超时、重试和重连策略。本轮三十秒内恢复写入口的结论，建立在连接超时不超过两秒的条件上。

## 现在可以怎样介绍 PostgreSQL 支持

对外介绍时，可以明确写成下面这段话。

> ClusterGuard HA 2.2 已支持原生 PostgreSQL 流复制高可用。目前已完成 PostgreSQL 16.4 三节点实验室验收，覆盖发现、身份、拓扑、计划切换、自动故障切换、写 VIP、Raft 多数派保护、旧主 `pg_rewind` 回挂、审计和报告。生产使用前仍需按客户现场环境完成准入测试。

有几句话暂时不能写。

- 不能宣称 PostgreSQL 12 到 19 已经全部通过认证
- 不能把异步流复制描述成零数据丢失
- 不能把一次实验室时间写成所有客户的固定 RTO
- 不能把高可用切换代替备份、归档和时间点恢复
- 不能在没有现场隔离验证时承诺任意网络分区都能自动接管

版本边界写清楚，会让产品介绍少一点热闹，却能让上线决策更可靠。

## 多数据库平台终于迈过了第一道门

MySQL 2.1 验证了 ClusterGuard HA 的控制内核。PostgreSQL 2.2 进一步证明，同一套资源模型和安全工作流能够容纳另一种数据库，同时保留它自己的身份、复制和恢复语义。

这一步对产品很重要。用户先在统一控制台看到结果，操作锁、授权、端点所有权、验证、审计和报告则由控制内核统一处理。数据库原生身份、候选判断、角色切换和旧主恢复继续由各个 Adapter 按引擎语义实现。

Oracle Data Guard Broker 与 SQL Server Always On 仍然要走各自的 Adapter、故障矩阵和认证流程。PostgreSQL 的验收结果不能替它们背书。ClusterGuard HA 会继续按同一个原则推进，功能可以慢一点，证据必须跟上。
