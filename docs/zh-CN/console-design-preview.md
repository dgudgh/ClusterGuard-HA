# 控制台本地设计预览

日期：2026-09-08。此轮只交付 HTML 供人工确认，不生成新 RPM 或升级包，不部署现场。

## 设计范围

- 保留经典白底、浅灰背景和蓝色操作色，不使用已否决的纸感米白主题。
- 八个主页面统一导航、Lucide 图标、标题、页签、表格、状态标签与弹窗。
- 总览保留搜索和健康筛选优化，新增按引擎资源摘要和最近 5 次操作。最近记录是首页摘要，完整审计日志仍全部保留。
- 拓扑节点左对齐，主库有蓝色边线；连接线与节点中心对齐。窄屏优先显示健康状态。
- 指标页增加当前采样的节点数值对比，不伪造历史曲线；缺失采样不显示成零。
- 升级窗口保留签名校验、校验前禁用操作、圆形步骤、固定摘要和独立滚动日志。
- 不修改数据库恢复、fencing、Raft、授权、健康判定或升级执行行为。

## 本地文件

`preview/console-redesign/index.html` 是可直接打开的单文件 HTML。

生成器：`tools/build-console-preview.cjs`。数据仅来自隔离 fixture，使用 sample 集群名与保留示例 IP。页面内嵌全部示例响应，CSP 禁止网络连接和表单提交；未提供执行证据的动作明确失败，不假装数据库操作成功。没有现场凭据。

原有加载竞态、慢辅助接口、超时、操作锁定、升级日志滚动回归使用 `tools/console-ui-acceptance.cjs`。大日志性能回归使用 `tools/console-latency-acceptance.cjs`。这些是本地测试，不等于现场升级验收。

## 现场 PG 刷新速度补充诊断

2026-09-08 17:25，使用独立 Chrome 页面、Network 面板，对 `https://192.168.102.152:3000` 执行只读页面刷新。现场版本确认为 2.2-91。未 SSH，未执行切换、恢复、上传或升级。

| 请求 | MySQL | PostgreSQL 第一次 | PostgreSQL 复测 |
| --- | ---: | ---: | ---: |
| 集群详情 | 7 ms | 86 ms | 21 ms |
| 拓扑 | 6 ms | 82 ms | 21 ms |
| 健康 | 4 ms | 6 ms | 3 ms |
| 候选 | 2 ms | 2 ms | 3 ms |
| 指标 | 3 ms | 3 ms | 2 ms |
| 操作摘要 | 4 ms / 1.7 KB | 292 ms / 442 KB | 285 ms / 442 KB |

结论：本次可复现的主要差异在操作摘要请求，不是数据库引擎查询性能对比。2.2-91 已先绘制拓扑，但 `loadSelectedCluster` 的健康、候选、指标、操作摘要仍一起等待，等待摘要期间保留操作锁和核对提示。因此 PG 历史摘要的较大体积拖慢了刷新收尾。现场全局日志显示 413 个事件、517 条原始记录，不能把记录数解释成当前故障数。

上述设计初版尚未修复该剩余瓶颈。后续修复及验证见下文，现场仍需人工更新后复测。上述时间是两次读取样本，不代表长期 SLA。

## GitHub 历史核对与刷新修复

2026-09-08 通过已连接的 GitHub 接口读取私有仓库 `dgudgh/ClusterGuard-HA`，没有推送、创建发布或修改分支：

- [14defea: add guarded operations console](https://github.com/dgudgh/ClusterGuard-HA/commit/14defea07f158e5e0ff4a3ae73edcf783870d026) 的 diff 明确把 `GET /operations?cluster_id=...` 加入健康、候选和指标的 `Promise.all`，并把全量日志加入启动等待。该提交前的相应刷新代码没有操作历史请求。
- [v2.2.68](https://github.com/dgudgh/ClusterGuard-HA/releases/tag/v2.2.68) 对应 `bc0546a3e91ac86c61017d6d57c7ceeedd3d114f`。核对时这是远端最新发布，也是 `codex/2.2-postgresql` 分支 HEAD。本地后续改动尚未进入该远端分支，不能把 GitHub 最新发布当作现场 2.2-91 源码。
- 当前 2.2-91 将全量记录改成全量摘要、先绘制拓扑，但仍等待摘要才结束刷新。没有旧版同期同数据的现场样本，不能仅凭提交历史断言用户每一个旧版本的实际耗时。

本次局部修复：

1. 新增只读 `GET /api/v1/operations?view=context`。按集群返回完整计数及所有历史主库身份；全局返回完整计数和最近 5 次活动。Store 在同一个读锁内投影，不克隆完整执行证据，保留全部原始记录。
2. 集群刷新只等拓扑、健康、候选、指标和轻量上下文。上下文读取失败、旧服务器返回数组、集群身份不符时都不能解锁操作。此上下文不作为后端执行授权，fencing、仲裁、审批与服务端检查没有改动。
3. 全局近期活动独立加载。完整日志仅在进入日志页、主动刷新或操作后按需读取；读取失败单独显示。切换集群不再重建隐藏日志列表，不重置已展开详情和加载更多位置。
4. 记录数量不受安装包保留 3 个版本的策略影响。首页最近 5 次仅为显示摘要，日志页仍提供全量筛选、分页展示和原始证据。

## 同条件对照

`tools/console-context-acceptance.cjs` 使用修改前本地 2.2-91 页面与修复后实际页面，同一隔离 fixture、1,000 条记录、同样人为增加 2,400 ms 历史请求延迟。以下不是现场实测，不是数据库查询性能或升级验收结论：

| 条件 | 修改前 | 修复后 |
| --- | ---: | ---: |
| 启动到刷新完成 | 4,931 ms | 70 ms |
| 第一次切到 PG | 2,514 ms | 37 ms |
| 切回 MySQL | 2,428 ms | 16 ms |
| 再次切到 PG | 2,420 ms | 16 ms |
| 历史请求未返回时切 MySQL / PG | 受历史等待影响 | 27 / 16 ms |

验收同时断言：1,000 条完整日志仍可读；最旧的 running/indeterminate 记录计数正确；旧主身份不因最近 5 条限制丢失；日志失败不阻断拓扑刷新；原始证据惰性读取；缺上下文保持锁定；旧集群迟到响应不能覆盖新集群。报告与截图：`.build/console-refresh-context/performance/`。

本轮通过 `go test ./internal/api ./internal/store`、操作上下文/摘要的 `-race` 测试、原有页面加载回归，以及八个页面五种宽度的 101 张截图检查。单文件 HTML 已重新生成，仍完全离线且拒绝写请求。没有生成新升级包，没有安装到现场，因此不能声称现场已消除卡顿。
