# 滚动升级维护门禁失败复盘（2026-09-07）

## 事件摘要

- 升级路径：`2.2-68` 到 `2.2-69`
- 失败阶段：建立集群维护门禁，进度 8%
- 结果：升级包签名校验、版本合同校验和三节点分发均成功；没有节点安装目标 RPM。
- 自动处置：维护门禁已释放，控制面恢复运行。
- 制品结论：`2.2-69` 不得再次执行，也不得覆盖同名制品；修复使用新发行序号。

## 现场证据

三个控制节点均已就绪、识别同一 Leader、确认多数派并保持相同 Raft 索引。失败时唯一活动操作为：

```text
operation_id = f594c1b0-2265-4967-b8d7-399938d84866
engine       = mysql
kind         = failover
requested_by = clusterguard-automatic-recovery
stage        = plan
status       = running
updated_at   = 2026-09-04T07:52:52Z
```

该记录已停留三天。`plan` 位于 Adapter 执行之前，没有开始数据库变更，也没有活动的分布式操作租约。旧升级器只返回“控制面未就绪、无多数派、维护状态不一致或仍有活动任务”的合并错误，并把第一个检查节点写进错误信息，导致现场看起来像 PostgreSQL 节点或控制面健康异常。

## 根因

Durable Workflow 先持久化 `plan/running`，再写计划审计。进程中断或计划审计失败时，旧代码直接返回错误，没有把已经创建的运行记录写成终态。运行时也没有对失去执行器的历史 `running` 记录做恢复收口。

维护门禁要求 `active_operations=0`，这是正确的安全规则。问题不在门禁过严，而在旧任务没有终态，以及诊断把多个条件压成一句话。

## 修复原则

1. 执行前审计失败立即原子写入终态，不能留下 `running`。
2. Leader 周期性恢复超过 30 分钟且没有活动操作租约的记录。
3. `discover` 到 `approve` 阶段可安全收口为 `failed/abandoned_pre_commit`。
4. `execute` 及之后默认收口为 `indeterminate` 并要求人工复核；只有持久化验证明确通过时才能写成功。
5. `promoted_unverified` 必须保留原失败分类，继续走既有的受控恢复路径。
6. 陈旧判断、元数据 revision、运行状态和操作租约必须在同一个 Store/Raft 快照提交内检查，不能先读后写。
7. 升级器只在维护门禁已经由全部节点确认后，临时识别“自动恢复、执行前阶段、超过 30 分钟”的旧记录；不删除、不修改操作记录，等待新 Leader 运行时原子收口。
8. 人工操作、新鲜任务、`execute` 之后的任务、`indeterminate`、生命周期任务和无法读取的操作清单继续阻断升级。
9. 新 Leader 收口完成前不得释放维护门禁；最终验收仍严格要求 `active_operations=0`。

## 发布门禁

- 必须运行 Workflow、Store、Runtime 和升级脚本的正反例测试。
- 必须独立验证 RPM、升级包签名、包内 SHA-256 和引导升级器摘要。
- 必须在当前 Leader 控制台真实选择并上传 `.cgupgrade`，确认来源版本、目标版本和签名状态。
- 上传校验不能替代生产执行；生产滚动升级必须单独获得确认。
- 禁止用直接安装 RPM 代替用户上传、确认和滚动升级流程。

## 敏感信息

诊断只允许输出操作 UUID、集群 UUID、类型、阶段、状态和更新时间。控制 Token、密码、Cookie、连接串、passfile 和完整环境变量不得进入日志、API 错误或支持包。

## 2.2-70 现场复测补充

2.2-70 在真实 Chrome 中上传、签名和兼容性校验均通过，但第一次点击“滚动升级”后仍在只读计划阶段等待。原始输出确认三个控制节点唯一违反项仍为 `active_operations_not_zero`，对应同一个陈旧自动恢复 `plan/running` 记录。

时间线从 15:10:52 持续到 15:13:05，约 133 秒。配置中的“60 秒”只统计了 30 轮之间的休眠，没有统计每轮三节点 SSH 和 API 探测耗时。

进一步根因是兼容豁免仅在维护门禁建立后生效，而控制台强制要求先生成只读计划。只读计划继续等待 `active_operations=0`，形成循环依赖。2.2-70 因此被否决，不得再次执行。

2.2-71 允许只读计划对同一严格分类的陈旧自动恢复执行前记录立即生成节点顺序。该阶段不建立维护门禁、不修改 Operation、不分发或安装 RPM。人工、新鲜、执行后、不确定和不可读记录仍然失败关闭；生产执行仍须建立维护门禁，并在新 Leader 启动后严格验证任务已原子收口。

## 2.2-71 真实执行失败补充

2.2-71 在 Chrome 中完成上传、验签、只读计划和补丁 ID 二次确认后，真实滚动执行到首个混合节点 `192.168.102.152`。目标 RPM 已安装，但节点就绪检查等待结束后失败；自动回退重新安装 2.2-68 后又被同一就绪条件阻断，因此三个控制节点继续保持软件升级维护门禁。

旧脚本没有输出 RPM 与各 systemd 单元的组合状态。结合 RPM 事务提示“服务尚未自动启用”和就绪合同可确认，脚本只重启 HA、Helper 和 Agent，没有显式恢复并验证 `clusterguard-agent-reconcile.timer` 的启用状态。2.2-72 在 RPM 事务后按节点角色显式启用服务和 Timer，并把真实墙钟超时及服务状态写入脱敏诊断。

随后通过控制台发起同一 2.2-71 补丁的受控回退。三个节点均报告 `update_maintenance_active=true`，但旧脚本把该动作按新任务处理并要求维护状态为 false，于 RPM 变更前以 `maintenance_state_mismatch` 拒绝。这是第二个状态机缺口：同补丁回退没有复用它自己留下的完整维护锁。

2.2-72 对该路径增加以下合同：

1. 同补丁回退只在全部控制节点的 lock、patch ID 和维护 JSON 完整一致时复用既有门禁。
2. `resume` 只接受同补丁 3/3 完整门禁；零锁、部分锁、错误 patch 或缺失标记均不自动修补。
3. 复用和旧失败任务接管的门禁在前置检查失败或进程退出时必须保留。
4. 维护门禁释放前建立 Raft 维护记录，在所有本地标记删除期间持续阻断自动变更，最后由最新 Leader 原子释放。Leader 最后删本地标记本身不足以防止中途再次选举。
5. 2.2-71 标记为现场拒绝；2.2-72 必须重新执行完整三节点 Chrome 升级才能转为通过。

2026-09-07 17:30 左右再次直接核对三台主机：152、153、154 的 RPM 都是 2.2-68；HA、Helper、Agent 均 active，Reconcile Timer 均 inactive。升级前置验收今后必须覆盖 Timer inactive 的实际组合，不能只模拟 RPM 版本变更。

并发回归还必须覆盖：回滚期间不提前发布 failed；失败任务执行 ID 接管；首个本地标记释放后重新选举；部分释放失败后的回锁；旧版本不支持 Raft 门禁时保持维护；异常退出后界面仍能读取最终失败事件。安装包只保留最近三个版本，审计和升级事件不按这个数截断。

## 2.2-73 最终浏览器验收

2.2-68 到 2.2-72 已通过真实上传、计划确认和三节点升级，但成功后页面又选中历史 2.2-71 的 `maintenance_active=true` 记录，错误显示仍在回退。这是独立的前端状态选择缺陷，不能把 RPM 安装成功当成整条用户流程成功。

2.2-73 改为按最新实际执行时间选择任务，并同步查询控制面的当前维护状态。新上传和计划不掩盖旧未完成执行；真正存在的维护门禁仍按失败关闭处理。历史失败和原始日志不删除。新增测试执行实际页面 JavaScript，覆盖旧失败、旧运行、只读计划、未知门禁和最新成功等组合。

2026-09-07 17:56:00 至 17:57:22，通过 Chrome 上传的 2.2-72 -> 2.2-73 正式执行共 82 秒。153、154、152 分别在 12、12、13 秒内完成安装和就绪；三台正式 RPM 和进程均为 2.2-73，四项必需服务 active/enabled，维护标记与临时 systemd 入口均已撤销，最新 Leader 确认 3 个投票节点且无遗留活动任务。重新加载后成功状态不再回弹，进度展开/收起通过。
