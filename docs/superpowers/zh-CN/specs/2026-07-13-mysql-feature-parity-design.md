## 目的

ClusterGuard HA 将独立实现此前原型所验证的生产级 MySQL 能力。此前的代码库仅作为行为逻辑和测试场景的参考。不会复用任何源代码包、API、元数据表、二进制文件、配置键、命令名称或产品标识。

交付目标是一个由奇数个 ClusterGuard 控制器管理的三节点 MySQL 高可用集群。运维人员必须能够通过单一控制台发现集群、选择晋升候选节点、将主库切换与虚拟 IP（VIP）漂移作为原子操作执行、修复已恢复的前主库、添加或移除节点、修正可变元数据、检查性能指标，并对所有操作进行审计。

## 不可妥协的安全规则

- 平台 UUID 是唯一的持久化资源标识符。主机名、IP 地址、端口和显示名称均为可变坐标。
- 原生 MySQL `server_uuid` 将观测数据绑定到现有实例。
- 数据库变更操作始终遵循 DISCOVER -> PRECHECK -> PLAN -> SAFETY_GUARD -> LOCK -> APPROVE -> EXECUTE -> VERIFY -> AUDIT -> REPORT 流程。
- 写入角色变更及其对应的活跃 VIP 变更属于同一原子操作。除非独立验证恰好存在一个可写的 MySQL 实例且恰好有一个 VIP 所有者，否则操作不可能成功。
- 未知的探测覆盖率、未知的控制器多数派仲裁（quorum）、过时的拓扑结构、未隔离的旧主节点或冲突的租约所有权均会阻塞变更操作。
- 在可能的提交点之后的操作，若验证未完成则返回 `indeterminate`。它们绝不会仅因命令退出码为零而被报告为成功。
- 密钥在服务端解析，按用途分离，从持久化资源中脱敏，且绝不接受作为 CLI 参数或请求字段。
- 不支持的行为返回 `unsupported`；不会将模拟的成功暴露为真实操作。

## 能力对等矩阵

| 能力 | ClusterGuard 实现方式 | 完成证据 |
| --- | --- | --- |
| 资产发现 | MySQL 适配器探测已注册的端点 | 主机名/IP/端口变更后资源 UUID 保持稳定 |
| 拓扑与健康状态 | 原生复制链路、角色、线程、延迟、GTID 及探测覆盖率 | 包含一个主节点和两个副本节点的三节点快照 |
| 候选者评估 | 确定性资格判定与数据丢失风险排序 | 选定的目标为健康的直接副本，且无异常 GTID |
| 计划内切换 | 源节点隔离、GTID 追赶、目标提升、所有副本重新指向新主 | 新主节点就位，所有从节点健康，VIP 仅指向目标 |
| 故障切换 | 稳定的故障窗口、多数派仲裁租约、隔离证据、最佳候选者提升 | 旧主节点无法写入；存在一个新写节点和一个 VIP 持有者 |
| 原主节点恢复 | 安全时快速重新附加 GTID；分歧时重建路径 | 原主节点处于只读状态并跟随当前主节点 |
| 低风险修复 | 刷新、收集状态、启动 IO/SQL 线程、维护状态 | 变更白名单加上验证与审计 |
| VIP 生命周期 | 状态查询、获取、释放、转移、验证、定期协调 | 集群范围内唯一所有者与当前主节点匹配 |
| 脑裂防护 | 控制器多数派仲裁、短租约、多观察者探测、本地自我隔离 | 少数派节点移除 VIP 并保持只读状态 |
| 重启收敛 | Agent 启动保护与定期协调 | 重启后 VIP 仅返回至已验证的主节点 |
| 元数据协调 | 协调更新、别名、重复/原生身份检查 | 主机名或端口变更后无重复资源 |

| 数据节点生命周期 | 安装、初始化、同步、注册、验证、移除 | 新增节点作为健康的副本出现，无需手动执行 SQL |
| 旧节点重建 | 相同的生命周期工作流，保留资源槽位 | 修复后的主机复用资源 UUID 并重新加入为副本 |
| 控制器生命周期 | 原子的奇数成员扩容/缩容 | 无已提交的偶数控制器集合 |
| 数据同步 | 根据能力选择克隆、XtraBackup 或逻辑转储回退 | 记录方法、源、进度和验证结果 |
| 指标 | 原生 JSON 和 Prometheus 输出，以及监控安全的扁平 JSON | QPS、TPS、连接数、线程、慢查询、缓冲区和延迟指标 |
| 运维 UI | 集群选择器、拓扑图、受控切换、旧主库修复、节点生命周期 | 每个可见操作均调用真实 API 或处于禁用状态 |
| 审计与报告 | 操作时间线、原始证据、JSON/HTML 报告 | 源、目标、时间、操作员、检查点和验证结果可见 |
| 安装 | 单一软件包、预检、systemd、logrotate、控制器/数据节点角色 | 全新三主机安装通过冒烟测试和恢复测试 |


## 架构

### 控制平面

控制平面负责资源标识、操作状态、不可变计划、控制器多数派仲裁、租约、审批、锁定、审计、报告以及 API 行为。
它从不直接运行引擎特定的 SQL。持久化操作引用集群 UUID、源和目标实例 UUID、精确的拓扑观察结果、资源修订版本以及计划摘要。

控制器集采用奇数成员规则。一个Leader对变更操作和租约授予进行序列化。跟随者处理只读请求，并拒绝或重定向变更操作。多数派仲裁丢失会阻止新的变更操作，并导致没有有效可续期租约的具备 VIP 能力的代理进行自我隔离。

### MySQL 适配器

适配器负责处理 MySQL 方言差异和引擎证据：

- MySQL 5.7 使用 `SLAVE`、`MASTER`，并通过节点代理实现显式角色持久化。
- MySQL 8.x/9.x 使用在运行时发现的可用 `REPLICA`、`SOURCE` 和持久化变量语法。
- GTID 模式对于自动切换、故障转移和快速重新附加是强制性的。
- 适配器构建确定性计划，但不能授予锁、审批、租约或审计豁免。
- 复制凭据与发现和运行凭据不同，仅用于 `CHANGE ... SOURCE/MASTER TO`。

### ClusterGuard 代理

`clusterguard-agent` 是一个安装在每个受管数据节点上的小型特权辅助程序。它仅暴露经过身份验证且列入白名单的命令契约：

- 报告 VIP 所有权和接口状态；
- 添加或移除一个配置的集群 VIP；
- 在获取后发送免费 ARP；
- 跨重启持久化 MySQL 只读角色状态；
- 运行本地自我隔离操作；
- 执行来自已签名控制器计划的生命周期阶段。

该代理验证集群 UUID、操作 UUID、租约 UUID、VIP 地址、接口、前缀、实例 UUID 和计划摘要。它不暴露通用的 shell 命令端点。控制器到代理的传输使用固定的主机密钥和专用的服务身份。无法访问的代理被视为未知证据，并阻止新的 VIP 所有者选举。

### 写入端点提供者

Linux VIP 提供者解析所选集群的活跃 `HAEndpoint` 以及所有清单主机。`Precheck` 探测每一台主机，仅在当前所有者集合已知且与计划源状态一致时才通过检查。`Transfer` 执行以下操作：

1. 验证操作持有活跃集群锁和端点租约；
2. 从每个观察到的非目标所有者中移除 VIP；
3. 验证所有者数量为零；
4. 在目标节点上获取 VIP 并发送免费 ARP（Gratuitous ARP）；
5. 验证所有观察者仅确认目标节点拥有所有权。

如果在计划切换期间、目标节点启用写入之前，目标获取失败，提供者可能会将 VIP 恢复到仍处于隔离状态的源节点。一旦目标节点变为可写状态，故障即为不确定状态，需要通过正常的验证/协调路径进行处理。

## 凭据

每个 MySQL 集群引用的是密钥名称，而非密钥值：

- `discovery`：进程列表、复制状态、变量、指标；
- `operation`：只读隔离、角色转换、停止/启动/重置副本；
- `replication`：复制通道身份验证；
- `install`：主机引导和节点同步。

默认的环境密钥存储解析命名凭据。API 拒绝用户名/密码字段。后续的密钥存储提供者可以在不更改适配器的情况下实现相同的接口。

## 计划切换状态机

三节点计划切换流程如下：

1. 重新验证资源清单、原生身份标识、修订版本、探测覆盖范围、GTID、复制链路、目标资格、控制器多数派仲裁以及 VIP 所有权；
2. 使用 `super_read_only` 和 `read_only` 对源节点进行隔离（fence），然后持久化该状态；
3. 捕获被隔离源节点的 GTID，并等待策略要求的所有健康副本达到该 GTID，其中选定的目标节点必须达到此位置；
4. 停止/重置目标节点的复制通道，并将其设置为可写状态；
5. 配置原源节点及所有同级副本以 GTID 自动定位方式跟随目标节点，然后启动并验证两个线程；
6. 在端点租约下转移 VIP；
7. 刷新发现服务，并验证存在一个可写主节点、所有从节点均关联至其原生 UUID、延迟处于有界范围内，且仅有一个 VIP 所有者；
8. 原子性地发布最终审计事件并生成报告。

操作日志记录每个幂等步骤。重启时通过检查步骤的后置条件来恢复，而非盲目重放变更操作。

## 故障转移与自动恢复

故障恢复是一种独立的操作类型。默认情况下，它需要稳定的 30 秒观察窗口、六次间隔五秒的检查、控制器多数派仲裁、健康的候选节点、全新的独占端点租约，以及隔离或等效证明以确认旧主节点无法提供写入服务。数据丢失风险最低的候选节点将被提升为主节点。其余可达的副本将重新指定父节点（reparented），并转移 VIP。如果旧主节点未被隔离或不可观测，即使导致暂时不可用，操作也将保持阻塞状态。

每个数据节点代理定期协调本地状态。缺乏多数派可见性或没有其本地实例活动租约的节点将移除 VIP 并强制设为只读。因此，恢复后的旧主节点无法作为第二个写节点或 VIP 所有者返回。

## 原主节点恢复与修复

恢复流程首先验证当前主节点、目标原生身份、无本地 VIP、只读状态、GTID 关系以及不存在错误事务。如果原主节点的已执行集合是当前主节点的子集，则通过 GTID 自动定位将其附加。如果出现分歧，工作流将阻止快速重新附加，并提供节点同步/重建计划。副本 IO 和 SQL 线程的启动是唯一直接的低风险复制变更；在未经签署的修复/重建计划之外，跳过事务、重置数据或更改源操作均被阻止。

## 节点生命周期

数据节点和前节点的重建使用统一的生命周期工作流：

`PREFLIGHT -> INSTALL -> INITIALIZE -> SYNC -> CONFIGURE_REPLICATION -> REGISTER
-> DISCOVER -> VERIFY -> COMMIT_METADATA`。

同步方式的选择由能力驱动：

1. MySQL Clone，当源/目标版本和插件状态兼容时；
2. XtraBackup，当已安装的匹配二进制文件支持该发行版时；
3. 逻辑转储作为缓慢的回退方案。

数据节点数量不受限制。控制器和混合节点成员数必须为奇数，并且仅在所有新控制器健康后才提交。移除会导致失去多数派仲裁（quorum）的主节点、活动 VIP 所有者、同步源或控制器将被阻止。

## 元数据协调

元数据 API 和拓扑模式接受可变的主机名、IP、端口、显示名称、别名和端点更正。预检查会探测提议的端点，并要求相同的原生 `server_uuid`。匹配的原生身份将更新现有资源，并将之前的坐标作为别名退役。重复的活动坐标、分配给不同资源的重复原生身份、服务器 UUID 更改或未注册的目标均被阻止。

## API 扩展

现有的 `/api/v1` 资源和操作路由仍作为标准接口表面。MySQL 功能对等工作新增了面向资源的路由：

- `GET/POST /api/v1/clusters/{id}/ha-endpoints`
- `GET /api/v1/clusters/{id}/vip/status`
- `POST /api/v1/clusters/{id}/vip/reconcile`
- `POST /api/v1/operations/former-primary-rejoin/*`
- `POST /api/v1/operations/repair/*`
- `POST /api/v1/nodes/sync/{precheck,plan,execute,verify}`
- `POST /api/v1/nodes/{precheck,plan,execute,verify}`
- `GET /api/v1/operations/{id}/timeline`
- `GET /api/v1/reports/{id}` 和 `/api/v1/reports/{id}/html`
- `GET /api/v1/monitoring/health` 和 `/api/v1/monitoring/metrics`

所有 POST 路由均需要控制平面认证。涉及状态变更的操作路由还需要工作流锁、审批策略以及计划摘要；调用方不得直接调用代理程序。

## 控制台

控制台包含六个工作界面：

1. 概览：集群级别的集群健康状态、风险、延迟、写入节点、VIP 所有权以及活跃操作，不渲染拓扑图。
2. 拓扑：选定集群的节点、不可变标识、可变坐标、角色、版本、延迟、复制边、VIP 所有者以及元数据模态框。
3. 操作：选定集群、当前主节点、可选候选节点、VIP、延迟、一次受控切换操作以及原主节点恢复。
4. 节点：添加/移除/重建数据节点和控制节点，并显示阶段进度。
5. 指标：内置 MySQL 性能、复制健康状态、告警阈值、JSON 和 Prometheus 端点。
6. 操作日志：源、目标、操作员、时间、状态、验证、报告以及折叠的原始证据。

可见控件由能力驱动。被阻止的操作会解释具体失败的检查项；绝不会静默无响应。

## 验证策略

每个行为均采用测试驱动开发（Test-First）模式。单元测试涵盖方言、执行计划、租约、端点唯一性、候选节点及 GTID 逻辑。工作流测试涵盖网关顺序、幂等恢复、崩溃点、审计/报告原子性以及不确定结果。HTTP 测试涵盖身份验证及对敏感字段的拒绝处理。Agent 测试使用隔离的网络命名空间或命令模拟（fakes）。实验室测试在 `192.168.102.152-154` 上运行，包括重复的轮询和随机切换、控制器/数据库重启、网络分区、陈旧 VIP、前主节点恢复、元数据变更以及节点重建。

## 交付顺序

完整范围以独立可发布的增量方式实现：

1. 凭证分离、高可用端点清单、Agent 及真实 VIP 提供者；
2. 三节点计划内切换及前主节点重新加入；
3. 故障转移、法定租约、自我隔离及自动恢复；
4. 修复操作及节点生命周期；
5. 指标、操作时间线、控制台、安装程序及破坏性实验室矩阵。

在真实实验室路径成功且所有不支持的路径均安全失败（fail closed）之前，任何增量均不视为生产就绪。
