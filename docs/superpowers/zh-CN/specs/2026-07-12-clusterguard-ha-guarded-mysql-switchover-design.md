# ClusterGuard HA 受保护 MySQL 切换设计

<!-- LANGUAGE-SWITCH -->
> **语言：** [English](../../specs/2026-07-12-clusterguard-ha-guarded-mysql-switchover-design.md) | 简体中文
<!-- /LANGUAGE-SWITCH -->

## 目标

在独立的 ClusterGuard HA 控制平面中实现第一个变更 MySQL 操作：受保护的计划切换内核。增量必须使操作状态持久化，计划不可变，重试幂等，终端结果可审计。在实际配置了真实写入端点提供者之前，不得暴露生产角色变更。

故障恢复、前主节点重新加入、节点生命周期执行、自动恢复以及 Linux VIP 提供者将作为后续项目单独进行，并返回明确的 `unsupported` 结果。

## 选定的交付边界

该增量通过面向能力的接口实现 MySQL 计划切换。测试使用确定性的假写入端点提供者来证明完整的角色变更序列。默认服务器没有变更端点提供者，因此在安全门或数据库副作用之前会拒绝执行，同时提供只读预检查和计划。

此边界防止 ClusterGuard HA 更改可写主节点但保留前主节点上的现有 VIP 或监听器的状态。

## 组件

### 持久操作注册表

平台仓资源清单储一个以不可变资源 UUID 为键的 `OperationRecord`。记录包含：

- 操作和目标资源 ID；
- 调用者提供的幂等键；
- 当前工作流阶段和终端状态；
- 拓扑观察令牌；
- 不可变操作计划和摘要；
- 计划引用的每个资源的元数据修订；
- 尝试次数、时间戳、失败分类和消息；
- 执行和验证摘要。

使用相同的幂等键创建相同的操作将返回现有记录。使用不同的集群、引擎、类型或目标重复使用该键将导致冲突。更新使用元数据修订的比较和交换，并通过仓库的原子快照协议进行持久化。

### 不可变计划

该计划仅从当前拓扑快照构建。它记录源主节点、选定目标、观察时间、源/目标元数据修订、有序的类型步骤以及对规范计划数据的 SHA-256 摘要。执行会拒绝缺少计划、摘要更改、观察令牌更改、资源修订更改或目标不同的情况。

计划的步骤如下：

1. 重新验证拓扑和资源清单成员资格；
2. 确认端点提供者的准备情况；
3. 在当前主节点上阻止写入；
4. 捕获主节点 GTID 位置；
5. 等待选定目标执行该位置；
6. 停止目标复制；
7. 将目标提升为可写；
8. 通过提供者转移写入端点；
9. 保持前主节点只读；
10. 验证恰好一个可写主节点和一个端点所有者。

将额外副本重定向和前主节点重新加入不隐藏在此增量中。当观察到的拓扑有额外副本时，计划会阻止执行，因为安全完成该拓扑属于前主节点/重新父节点项目。

### MySQL 操作上下文

公共请求仅包含资源 UUID。平台解析器加载选定的集群、当前拓扑快照、当前主节点、选定目标和配置的 MySQL 凭据。适配器接收此解析后的上下文；主机名和端口仅被视为可变连接端点。

MySQL 适配器从不接受来自任意 API 参数的主节点或目标端点，也从不控制超出持久化集群资源清单的实例。

### 写入端点提供者

`HAEndpointProvider` 独立于数据库适配器，提供以下功能：

- 能力和准备情况检查；
- 计划验证；
- 端点转移；
- 唯一所有者验证。

默认的不支持提供者没有副作用。假提供者仅在测试中存在。真实的 Linux VIP 提供者、租约、多数派仲裁、隔离令牌和网络分区行为将作为下一个交付项目。

## MySQL 预条件

只有在以下所有条件当前有探测证据时，计划切换才会通过：

- 所选集群中恰好存在一个可写主节点；
- 源和目标是该集群中的有效资源清单 UUID；
- 目标是当前主节点的可到达直接副本；
- 源和目标使用 GTID 模式 `ON`；
- 源和目标启用了二进制日志记录；
- 目标是只读的、可提升的且不在维护中；
- 复制 IO 和 SQL 线程正在运行；
- 观察到的延迟正好为零；
- 目标 GTIDs 不包含任何错误事务和缺失事务；
- 源和目标属于同一 MySQL 发布系列；
- 每个显式资源清单探测当前有效且健康；
- 没有其他副本需要重新父节点；
- 写入端点提供者可以执行并验证端点转移。

警告从不授权此第一个变更操作。任何未知证据都是阻止因素。

## 执行语义

工作流顺序是固定的：

```text
DISCOVER -> PRECHECK -> PLAN -> SAFETY_GUARD -> LOCK -> APPROVE ->
EXECUTE -> VERIFY -> AUDIT -> REPORT
```

在第一次变更之前，ClusterGuard HA 会持久化操作和计划。在获取集群锁后，它会重新验证确切的观察令牌、计划摘要、资源修订和实时 MySQL 预条件。

在变更之前，执行路径可以被上下文取消。一旦源已被隔离，取消会被记录，但执行器会继续执行达到安全、可验证状态所需的最小序列。每个完成的步骤在下一步开始之前都会被持久化。重试仅在重新观察并证明其后置条件之后才会跳过某一步。

MySQL 语法根据服务器能力选择。遗留的 5.7 语句和现代的 8.x/9.x 副本语句通过方言助手隔离，并分别进行测试。

## 故障语义

- 源隔离之前发生故障，数据库无更改，状态为终端 `failed`。
- 源隔离之后但目标提升之前发生故障，状态为 `blocked`；两个实例必须保持只读，需要人工审查。
- 目标提升之后发生故障，直到验证证明可写主节点和端点所有者，状态为 `indeterminate`。
- 端点转移失败时，新主节点尽可能保持只读，且从不报告成功。
- 数据库提交后，日志持久化不确定性保留现有的保守 `indeterminate` 协议。
- 不进行自动回滚，目标可能已接受写入后，旧主节点不会被重新提升。

原始 SQL、密码和命令参数不包含在操作、审计事件和报告中。

## API 行为

现有的只读 API 保持稳定。操作预检查和计划响应使用资源 UUID 和结构化检查。执行需要操作 ID、幂等键、选定目标 UUID 和审批令牌。

使用默认的不支持端点提供者时：

- MySQL 预检查和计划解释端点提供者阻塞器；
- MySQL 执行返回 HTTP 501，状态为 `unsupported`；
- PostgreSQL、Oracle 和 SQL Server 的行为保持不变；
- 不发生锁定、SQL 修改或端点命令。

操作记录及其审计/报告时间线在重启后可以查询。

## 验证

验证独立探测源和目标，并向端点提供者请求所有者证据。成功需要满足以下条件：

- 目标可访问、可写入，并且不再配置为副本；
- 源可访问且只读；
- 两个受控成员中恰好有一个是可写实例；
- 端点提供者报告恰好一个所有者，并且该所有者是目标；
- 存储的计划摘要和目标与验证的操作匹配。

任何未知的探测都会导致验证失败或不确定，从不成功。

## 测试

- 仓库测试涵盖幂等性冲突、CAS 更新、重启恢复、不可变计划和持久化失败；
- 适配器测试涵盖所有预检查和两种 MySQL 语法家族；
- 执行器测试涵盖正常路径、陈旧观察、陈旧元数据、隔离前失败、隔离后失败、提升后失败、重试和端点唯一性失败；
- 工作流测试证明门控顺序和所有门控通过前无修改；
- API 测试证明默认执行是失败即阻断的，操作记录仍然可查询；
- 竞争测试涵盖并发重复请求和操作更新；
- 清洁室扫描和所有现有的多引擎测试仍然是强制性的。

## 接受标准

1. 操作和计划状态在进程重启后仍然存在。
2. 重复的幂等请求不能执行两次。
3. 陈旧的观察、目标、计划摘要或元数据版本会被阻止。
4. MySQL 计划切换在确定性测试中通过完整工作流。
5. 在没有独立角色和端点验证的情况下，不报告成功。
6. 在没有真实端点提供者的情况下，默认运行时执行仍然不被支持，并且不产生任何副作用。
7. 故障转移、前主节点重新加入、节点生命周期和自动恢复仍然不被支持。
8. PostgreSQL、Oracle 和 SQL Server 的行为保持不变。
9. `go test ./...`、`go test -race ./...`、`go vet ./...`、清洁室扫描和配置验证通过。
