# ClusterGuard HA MySQL 能力迁移设计

<!-- LANGUAGE-SWITCH -->
> **语言：** [English](../../specs/2026-07-10-clusterguard-ha-mysql-capability-migration-design.md) | 简体中文
<!-- /LANGUAGE-SWITCH -->

## 目标

将经过验证的 MySQL 产品能力从冻结的原型中引入 ClusterGuard HA，作为独立设计的行为实现。不复制任何源代码、软件包、API、配置、持久化模式、二进制文件或运行时依赖项，也不进行兼容性封装。在整个工作过程中，PostgreSQL、Oracle 和 SQL Server 均保留显式的扩展点。

完整的 MySQL 产品路径必须允许运维人员发现集群、检查拓扑结构和复制风险、选择候选节点、执行受保护的计划内切换或故障恢复、将写入端点随新主节点移动、重新加入前主节点、添加或替换节点、验证结果，并检查完整的审计轨迹。

## 决策与替代方案

考虑了三种迁移方法：

1. 一个包含发现、切换、端点和安装逻辑的单一 MySQL 专用服务。这种方法初期开发速度快，但会阻止其他数据库引擎安全地共享控制平面。
2. 围绕冻结原型构建的兼容性外观（Facade）。这种方法能最快保留原有行为，但违反了独立内核的要求，并延续了基于端点的身份标识和隐式耦合。
3. 由通用工作流协调的能力导向型服务，其中引擎行为位于适配器之后，写入端点行为位于独立的端点提供者之后。

选择了第三种方法。它在保留 MySQL 行为的同时，确保数据库角色变更、端点所有权、主机配置以及平台协调能够独立测试。

## 架构边界

### 平台核心

平台核心负责管理不可变的资源 UUID、元数据修订版本、操作状态、计划、锁、审批、审计事件、验证记录、报告以及公共 API 契约。它不发出特定于数据库的 SQL 语句或操作系统端点命令。

### 数据库引擎适配器

`DatabaseHAAdapter` 负责特定于引擎的发现、拓扑解析、健康状态采集、候选节点评估、预检查、计划构建、角色切换、复制重新配置、旧主节点重新加入、节点同步验证以及操作后验证。

MySQL 通过 `server_uuid` 标识实例。主机名、IP 地址、端口、服务器 ID 和显示名称仍为可变元数据。任何端点坐标的变更均复用现有的资源 UUID。

### 写入端点提供者

写入端点的所有权不属于 MySQL 适配器。一个新的 `HAEndpointProvider` 契约负责管理 VIP 或未来的监听器/服务端点：

- `Capabilities()`
- `Inspect()`
- `Precheck()`
- `BuildPlan()`
- `AcquireLease()`
- `Assign()`
- `Withdraw()`
- `VerifyUniqueOwner()`

首个提供者实现了 Linux VIP 管理。未来的提供者可能实现数据库监听器、负载均衡器、云私有端点或其他写入地址机制，而无需更改数据库适配器。

### 节点配置提供者

一个独立的 `NodeProvisioner` 契约负责主机预检、数据库包安装、实例初始化、数据填充、服务注册以及退役。MySQL 适配器选择并验证复制语义；配置者通过显式的任务计划执行主机级工作。

### 控制器协调

控制器 Leader 权限、多数派仲裁（Quorum）、分布式操作锁、端点租约以及隔离令牌属于协调服务。单控制器模式使用具有本地持久化实现的相同接口。多控制器模式可在不更改工作流或适配器的情况下替换该实现。

## MySQL 能力集

### 发现与清单管理

- 发现 `server_uuid`、服务器 ID、版本、主机名、地址、端口、角色、只读标志、GTID 模式、二进制日志设置以及复制通道。
- 从源 UUID 到副本 UUID 构建复制链接。
- 检测端点别名、重复身份、陈旧端点、未管理节点、身份不匹配以及跨集群成员资格冲突。
- 在主库变更期间保持配置的集群名称稳定。
- 拒绝针对所选集群清单之外实例的控制操作。

### 健康与性能

- 收集可达性、主库可写性、副本 IO/SQL 线程状态、复制延迟、GTID 位置、异常事务、连接数、QPS、TPS、运行中的线程、慢查询率以及缓冲池命中率。
- 通过 JSON 和 Prometheus 文本端点发布与引擎无关的健康指标，无需外部导出器。
- 将健康状态分类为健康、降级、不健康或未知。未知的探测覆盖率绝不表示为健康。

### 候选评估

- 仅对可达且符合晋升资格的副本成员进行排名。
- 评估复制延迟、复制线程状态、GTID 一致性、异常事务、二进制/中继日志位置、维护状态、版本兼容性、只读状态以及数据丢失风险。
- 返回阻塞性检查项、警告信息、推荐候选节点、风险等级及预估数据丢失风险。
- 允许操作员选择其他符合条件的候选节点；绝不在静默状态下替换显式选定的目标节点。

### 计划内切换

- 确认当前主节点可达且运行稳定。
- 通过明确的计划步骤排空或阻止新的写入操作。
- 等待目标节点在配置的阈值范围内完成数据追赶。
- 晋升选定的目标节点，重定向副本节点，转移写入端点，验证端点所有权的唯一性，并将原主节点重新加入为副本节点。
- 将角色转换与写入端点转移视为包含补偿和验证步骤的统一工作流，而非两个独立的按钮操作。

### 故障恢复

- 在自动恢复前，要求具备控制器 Leader 权限、多数派仲裁（Quorum）、有效的操作锁以及当前的隔离令牌（Fencing Token）。
- 在可配置的时间窗口内并通过多个探测点确认故障状态。
- 当无法隔离旧主节点且无法证明写入端点唯一性时，阻止自动晋升。
- 晋升最佳符合条件的候选节点，重定向存活的副本节点，分配写入端点，验证拓扑结构，并报告任何状态仍为未知的节点。
- 在新主节点可写、副本节点跟随其同步，且写入端点恰好有一个已确认的所有者之前，绝不声明成功。

### 原主节点重新加入

- 通过 `server_uuid` 识别已恢复的节点，即使其主机名、IP 地址或端口已发生变更。
- 在评估和重新加入集群期间保持该节点为只读状态。
- 当 GTID 历史兼容时，选择增量 GTID 重新加入流程。
- 当历史发生分歧或本地数据不可信时，选择完整种子（full seed）工作流。
- 在将其标记为可用之前，验证其是否跟随当前的主节点。

### 节点添加、替换与移除

- 通过 Web 控制台和 API 添加数据节点、控制器节点或组合节点。
- 支持任意数量的数据节点。在生产协调组中强制要求控制器数量为奇数，并拒绝会导致失去多数派仲裁（quorum）的变更。
- 对修复后的物理节点和新节点使用统一的替换工作流：预检、安装、初始化、种子数据加载、启动复制、验证、更新元数据以及标记为可用。
- 通过能力选择的策略进行种子数据加载。在支持的情况下优先使用克隆（Clone），其次选择物理备份，逻辑转储作为受控的回退方案。
- 在退役节点前，检查其当前角色、写入端点所有权、复制依赖关系以及控制器多数派仲裁。

### 运维体验

- 控制台选择一个稳定的集群名称，然后将所有拓扑、操作、日志和报告请求限定在该集群 UUID 范围内。
- 拓扑视图展示每个清单成员的主机名、IP 地址、端口、版本、角色、延迟、健康状态以及写入端点所有权。
- 主要操作界面仅呈现候选者选择、当前主节点、写入端点、延迟、锁定状态以及相关的执行操作。
- 元数据编辑是拓扑视图上的模态框，通过元数据协调机制运行，而非直接修改存储的行记录。
- 操作日志显示开始/结束时间、源主节点、目标主节点、执行模式、最终状态以及折叠的原始响应。

## 统一操作模型

通用的 `OperationKind` 扩展以支持：

- `topology_refresh`
- `switchover`
- `failover`
- `former_primary_rejoin`
- `node_add`
- `node_replace`
- `node_remove`
- `metadata_reconciliation`
- `endpoint_reconcile`

能力按操作和阶段进行声明，而非通过一个粗粒度的 `execute` 标志。每个变更操作遵循：

```text
DISCOVER -> PRECHECK -> PLAN -> SAFETY_GUARD -> LOCK -> APPROVE -> EXECUTE -> VERIFY -> AUDIT -> REPORT
```

长时间运行的操作会持久化其阶段、尝试次数、租约/隔离令牌、检查结果、计划、执行输出以及验证结果。重复的 API 请求使用幂等键并返回现有操作。

## API 演进

现有的 `/api/v1` 读取路由保持有效。新的通用路由使用资源 UUID 和操作类型：

- `POST /api/v1/clusters/{id}/discover`
- `GET /api/v1/clusters/{id}/candidates`
- `POST /api/v1/operations`
- `GET /api/v1/operations/{id}`
- `POST /api/v1/operations/{id}/approve`
- `POST /api/v1/operations/{id}/execute`
- `GET /api/v1/operations/{id}/events`
- `GET /api/v1/clusters/{id}/metrics`
- `GET /api/v1/clusters/{id}/metrics/prometheus`

API 不暴露适配器特定的 SQL 或 Shell 命令。引擎特定的详细信息仅出现在结构化检查、计划步骤、指标和原始审计附件中。

## 可扩展性规则

- 工作流核心根据操作类型和能力描述符进行切换，而非引擎名称。
- 特定于引擎的字段存在于类型化的适配器详情对象或命名空间元数据中，绝不会出现在共享资源标识字段中。
- 写入端点和节点配置是独立于数据库引擎的提供者接口。
- 公共 API 使用通用资源和操作；适配器将它们转换为引擎操作。
- 不受支持的适配器阶段在获取锁之前以及产生任何外部副作用之前失败。
- 能力版本允许在不更改现有存储操作的情况下添加新的适配器方法或计划步骤类型。

## 错误处理与恢复

- 每个外部操作均记录开始时间、结束时间、目标资源、脱敏输入、输出摘要以及重试分类。
- 计划区分可重试的探测失败、阻塞性安全失败和不可逆的执行失败。
- 工作流重启仅在存储的计划、元数据修订版本、锁租约和隔离令牌仍然有效时，从持久化状态恢复。
- 过期的计划将被失效并必须重建；绝不会针对已更改的拓扑执行该计划。
- 密钥通过密钥 ID 或环境变量引用，绝不会写入计划、审计事件、报告或命令参数中。

## 交付分解

工作被划分为四个可独立测试的项目：

1. **MySQL 拓扑与候选节点智能**：完整的发现机制、复制链路、健康/性能指标、资源清单守护（inventory guards）、候选节点排名以及控制台拓扑视图。
2. **受守护的 MySQL 角色操作**：持久化的操作状态、计划内切换、故障恢复、原主节点重新加入、验证、审计及报告。在测试中，写入端点步骤最初使用模拟提供者（fake provider）。
3. **写入端点与控制器安全性**：Linux VIP 提供者、持久化租约、多数派仲裁/领导权检查、隔离令牌（fencing token）、唯一性探测、补偿机制以及自动恢复观察窗口。
4. **节点生命周期与交付**：供应者契约、主机预检、安装、种子策略、添加/替换/移除工作流、控制器组变更、Web 体验、打包及升级文档。

每个项目都会生成独立的实施计划和提交系列。后续项目仅依赖于早期项目中已提交的公共契约。

## 验证策略

- 单元测试使用伪造的 SQL 执行器、端点提供者、配置管理器、协调器和确定性时钟。
- 契约测试针对每个适配器运行相同的不可用支持、安全门控、幂等性、审计和验证套件。
- 集成测试为受支持的版本创建多实例 MySQL 拓扑，并验证发现、候选排名、切换、重新加入和端点所有权。
- 故障测试涵盖进程重启、网络分区、陈旧锁、陈旧计划、多数派仲裁丢失、模糊的旧主节点状态、重复写入端点和部分验证。
- 浏览器测试演练集群选择、候选选择、拓扑、受保护执行、操作进度、元数据协调和日志。
- 每次发布都必须进行洁净室扫描。

## 验收标准

- MySQL 功能完全在独立仓库中实现。
- 平台资源在主机名、IP 和端口变更时仍保持 UUID 寻址。
- MySQL 拓扑、健康状态、候选排名、角色操作、写入端点、前主节点重新加入和节点生命周期均由通用能力和工作流表示。
- 任何变更操作均不得绕过安全、锁、审批、验证、审计或报告机制。
- 自动故障恢复在没有领导权、多数派仲裁、隔离、旧主节点隔离和写入端点唯一性证据的情况下无法进行。
- PostgreSQL、Oracle 和 SQL Server 继续针对同一 SDK 编译，并在其能力添加之前返回明确的不可用支持结果。
- 首个实现项目可以独立发布为只读 MySQL 拓扑和候选评估升级。
